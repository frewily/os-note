# 第四讲（Aside）：LLM、Agents 与 Scaling Law

> 课程：JYY《操作系统》(2026)  
> 讲义：[Scaling Law 和 Agentic AI (Hacking Day)](https://jyywiki.cn/OS/2026/lect4.md)  
> 性质：补充选讲（Hacking Day），不属于考试内容；与操作系统实验和现代软件工程方法有关。

## 一句话主线

**LLM 用大规模参数从人类语言中学习世界模型；Agent 再为 LLM 接上记忆、规划和工具，使它能在“尝试—观察—修正”的循环中完成长期任务。Scaling Law 告诉我们，能够持续扩大数据、算力和反馈规模的通用方法，可能在跨过临界点后产生能力质变；但复杂项目最终仍依赖清晰的抽象、协议和验证。**

```text
LLM：理解并生成下一步
  + 工作区：跨轮次保存状态
  + 计划：把大任务分解
  + 工具：读写文件、运行程序、搜索、测试
  + 反馈：观察结果、发现错误、继续修正
  = Agentic Loop
```

## 1. “大、语言、模型”分别意味着什么

### 大：容量是承载复杂性的前提

一个很小的系统能保存和表达的信息有限。现实世界、自然语言和人类行为都非常复杂，因此模型需要足够多的参数和训练，才能容纳大量模式与关联。

这里的“大”不等于“大了就一定智能”，而是说：**若模型容量、数据或计算太少，它连复杂世界的规律都装不下。**

### 语言：人类已经整理好的世界模型

语言不是物理世界本身，而是人类几千年来形成的一套抽象：它舍弃大量细节，却保留了可交流、可复用的结构。不同人的经历不完全相同，但共享相似的物理和社会环境，因此可以用同一组词语对齐认识。

所以，模型学习海量语言时，不只是学习句法，也会间接学习文本背后的对象、关系、因果、规范和解题模式。语言的局限也同样明显：表达会丢失细节，文本知识不等于亲自感知和验证现实。

### 模型：根据上下文预测下一个 token

LLM 的基本形式看起来非常朴素：读入上下文，为下一个 token 建立概率分布，再选出一个 token，重复这一过程。

```text
已有上下文 → Transformer 计算 → 下一个 token 的概率分布
                                   ↓
                             生成一个 token
                                   ↓
                          放回上下文，继续生成
```

- **预训练**：在大量语料中学习“接下来通常出现什么”，形成广泛知识和模式；
- **后训练**：用指令数据、偏好反馈等，把模型调整为更会对话、遵守要求和完成任务的助手；
- **上下文（context）**：模型当前能直接注意到的信息，相当于有限的短期工作记忆。

“只是预测下一个 token”并不表示能力简单。若模型足够大、训练数据足够丰富，为了准确预测文本，它不得不学习文本背后的结构。复杂能力可能由这个简单目标间接产生。

## 2. LLM 怎样逐渐获得“眼睛、草稿纸和计算器”

单纯依靠参数和文本补全有明显限制，后来的系统为模型补上了更多能力：

| 类比 | 技术能力 | 解决的问题 |
| --- | --- | --- |
| 眼睛、耳朵 | 多模态输入，把图像、声音等与语言表示对齐 | 不再局限于纯文字 |
| 草稿纸 | Chain-of-Thought、计划和外部记录 | 把复杂问题拆成更简单的连续步骤 |
| 计算器/手脚 | 工具调用（代码、终端、搜索、文件等） | 不靠语言模型猜精确结果，而是让可靠工具执行 |

一步一步写出中间过程，相当于把有限的“心算”变成有外部记录的推导；调用计算器则进一步把不擅长的精确计算交给专用工具。关键不是模型什么都会，而是它逐渐学会：**什么时候该推理，什么时候该调用工具，怎样利用结果继续工作。**

## 3. Agent：让模型在循环中真正做事

Agent 不是另一个神秘模型，更像是一套让 LLM 持续工作的运行框架：

```text
读取目标和当前状态
        ↓
制定或更新计划
        ↓
执行一步：编辑 / 命令 / 搜索 / 测试
        ↓
观察真实结果
        ↓
成功则推进，失败则诊断和修正
        └──────────────↺
```

这就是 **Agentic Loop**。Agent 也会犯错；它的价值不在于“一次生成必然正确”，而在于能读取反馈、继续尝试，并最终收敛到可验证的结果。

### 工作区是长期记忆

模型每次启动时并不会天然记得过去所有工作，而且上下文长度有限。项目目录可以充当外部记忆：

- `README`、设计文档：说明目标、约束与架构；
- 计划和任务清单：记录做到哪里、下一步是什么；
- 源码和测试：记录当前实现与可执行的正确性要求；
- 日志和复盘：保留失败原因，但要压缩无用的大段输出；
- Git 历史：保存可恢复的项目快照，支持试验、比较和回退。

因此，Agent 工作质量不只取决于模型，还取决于工作区是否清晰、反馈是否可靠、历史信息是否被有效组织。

### 工具、Skills 与 Sub-agents

- **工具**：完成一次具体操作，例如查看文件、运行测试；
- **Skill**：把某类任务中可复用的经验、步骤与工具组织起来；
- **Sub-agent**：把边界清晰的子任务交给另一条独立工作流，可并行推进。

复用的重点不是堆很多工具，而是让每个工具有清楚的输入、输出和验证方式。

## 4. Scaling Law：规模增长为何值得重视

在 LLM 语境中，Scaling Law 是一种**实验观察到的规律**：在合理搭配模型参数、训练数据和计算量时，投入更多规模，训练损失通常会以较可预测的趋势下降。Kaplan 等人的研究和 Chinchilla 工作分别推动了对规模规律、算力与数据最优配比的理解。

这使研究者能先做小规模实验，再据趋势判断更大训练是否值得投入。它不是“模型越大必然产生任何想要的能力”，而是给出了一个可测量、可外推但仍需实验验证的方向。

### The Bitter Lesson（苦涩的教训）

Richard Sutton 总结的核心经验是：长期看，依靠更多计算与学习的**通用方法**，往往超过人为写入大量领域规则的精巧方案。人工经验不是没用，而是不应成为限制系统继续扩展的瓶颈。

课堂用几个历史例子说明这种规律：

- 存储容量增长到足以容纳海量网页，催生了大规模搜索引擎；
- 国际象棋中，搜索深度随算力增加，棋力稳定提升，最终出现 Deep Blue；
- AlphaGo 把学习、搜索和算力结合，突破了传统手写规则的上限；
- LLM 随数据、参数与算力增长，获得了越来越广泛的语言和任务能力。

### “量变引起质变”的正确用法

并非重复任何低效工作都有意义。真正重要的是找到一个**可扩展（scalable）**的方向：资源增加时，效果能持续、可测地改善，并最终跨过产生新用途的临界点。

```text
错误理解：重复低水平工作 × 更多次数 = 必然成功
正确理解：找到可扩展机制 + 更多数据/算力/反馈 = 持续改善的可能
```

衡量一个方向时可以问：

1. 增加数据、计算或并行尝试后，效果是否还能改善？
2. 改善能否被指标或测试真实测量？
3. 增长的成本是否可接受？
4. 规模扩大后是否会暴露新的瓶颈？

## 5. “Code is cheap” 后，人还需要学什么

当生成代码越来越便宜，价值会从“亲手敲出每一行”更多地转向：

- 判断真正要解决的问题，写清需求和约束；
- 把复杂系统拆成边界明确的子系统；
- 设计稳定的接口和协议，使组件能独立替换、复用和并行开发；
- 建立测试、日志和验证工具，让错误尽早暴露；
- 检查 Agent 的结论，不把“生成成功”误当成“运行正确”；
- 理解关键原理，才能在模型偏离目标时及时介入。

所以“AI 会写代码”不等于计算机基础没用了。相反，**基础知识从主要用于手写实现，转变为用于设计、审查、验证和纠偏。**

## 6. 为什么这节 AI 课又讲回了操作系统

复杂性分解依赖好的抽象，而前几讲正好给出了两个经典例子：

```text
应用生态 ← syscall → 操作系统实现
操作系统 ←  ISA   → 硬件实现
```

抽象把上下两侧的复杂性隔开：只要遵守稳定接口，两侧就可以独立演化。同样地，在普通软件中，系统与系统之间可以通过协议、文件格式、消息或 API 协作。

函数封装适合程序内部复用，但若所有模块彼此直接调用、共享大量内部结构，接口变化就会牵连许多文件，也不利于多个 Agent 并行修改。把大系统拆成职责单一的子系统，并用简单协议连接，能缩小每个 Agent 需要理解的上下文和改动范围。

> 好的抽象不是“文件越多、架构越复杂”，而是用尽量小而稳定的接口，隔离真正会变化的复杂性。

## 7. 课堂现场实验：让 Agent 写一个最小 OS

课堂将“实现一个最小 RISC-V OS 内核”的任务交给 Coding Agent。Agent 读取项目约定后，大致经历：规划任务、创建构建和链接文件、实现最小运行环境、线程及上下文切换、编译、读取报错并修复，最终在模拟器中运行。

这个演示证明的是：**对人类已有大量资料和成熟范式的问题，现代 Agent 已能生成并调试相当底层的代码。** 但它也暴露了局限：

- 容易沿着“立刻实现”的惯性一次写很多代码；
- 可能先堆实现，后补抽象和测试基础设施；
- 长时间命令会产生大量日志，浪费上下文；
- “能编译、能输出”只验证了部分现象，不等于设计、边界情况和正确性已经充分验证。

更成熟的协作方式是先提供清晰设计边界，再让 Agent 建立短反馈环：小步修改、快速构建、超时控制、精简日志、自动测试和关键状态验证。

## 8. 对当前学习方式的直接启发

可以把课程目录当成自己的学习工作区：

1. 每讲保留一份主线笔记，而不是复制全部讲义；
2. 用自测题做脱稿回忆，让“看懂”变成可检验的复述；
3. 把答错原因写下来，形成下一轮复习的外部记忆；
4. 让 AI 针对薄弱点解释、出题和纠错，但答案必须用讲义、实验或运行结果核对；
5. 长期保留学习状态，避免每次对话都从零开始。

这正是 Agentic Loop 的学习版：**目标 → 回忆/作答 → 得到反馈 → 修正理解 → 记录状态 → 下一轮。**

## 9. 课后 40 秒复述

LLM 通过大规模参数和语料，从人类语言这个高度压缩的世界模型中学习规律，本质操作是根据上下文预测下一个 token。多模态给它眼睛和耳朵，推理过程像草稿纸，工具调用像手和计算器。Agent 再用工作区保存长期状态，通过规划、执行、观察和修正的循环完成任务。Scaling Law 表明，在合理搭配数据、参数和计算时，扩大规模通常能带来可预测的性能改善；苦涩的教训强调可扩展的通用学习方法往往胜过手写规则。不过 Code is cheap 不代表设计和基础不重要：复杂项目仍要靠抽象、协议、测试和验证控制复杂性，这也正是 syscall 和 ISA 等操作系统知识提供的系统思维。

## 10. 自测题

1. 为什么“语言”适合作为模型学习人类世界的一种载体？它有什么局限？
2. LLM 的基本 next-token prediction 为什么可能产生复杂能力？
3. “眼睛、草稿纸、计算器”分别对应什么能力？
4. Agentic Loop 包含哪些核心环节？为什么 Agent 犯错不等于任务必然失败？
5. 工作区和 Git 为什么可以看作 Agent 的外部记忆？
6. Scaling Law 是什么？它不保证什么？
7. The Bitter Lesson 对设计 AI 系统有什么启发？
8. 为什么“量变引起质变”不等于“做什么都可以靠堆数量成功”？
9. AI 已能生成 OS 代码，为什么人仍需学习 syscall、ISA、测试和抽象？

### 参考答案

> 建议先脱稿回答，再展开核对；本讲重在形成方法论，不需要背论文曲线和人物年份。

1. 语言是人类长期形成的可交流抽象，文本中沉淀了对象、关系、因果和解决问题的方法，因此学习语言也能间接学习世界结构。它会丢失感官细节，而且文本可能错误、过时或存在偏见，所以语言知识不能替代现实观察与验证。

2. 为了在海量不同语境中准确预测下一个 token，足够大的模型需要学习语法、概念关系、常见推理和任务模式。这些内部表示能组合起来表现出翻译、编程等复杂能力；但输出仍是概率生成，不保证事实正确。

3. “眼睛、耳朵”对应多模态感知；“草稿纸”对应分步推理、计划和外部记录；“计算器/手脚”对应调用代码、搜索、终端等外部工具。

4. 核心环节是读取目标和状态、计划、执行一步、观察结果、判断并修正。Agent 单步可能出错，但只要反馈真实、错误可恢复、循环还能继续，它就有机会依据结果纠偏并逐步完成任务。

5. 文件保存目标、设计、代码、计划和测试，使模型在新一轮对话中能重新读取项目状态；Git 进一步保存各阶段快照，允许比较、分支试验和回退。因此长期状态不必全部依赖有限的上下文。

6. Scaling Law 是关于模型性能随参数、数据和计算规模增加而呈现规律性改善的经验关系，可用于预测扩大训练的收益。它不保证盲目增大模型一定经济，也不保证某个具体能力必然在指定规模出现。

7. 应优先构建能利用更多数据和计算持续学习的通用方法，谨慎把大量人工领域规则写死在系统里；不过人类仍要选择目标、提供数据、设计反馈和验证结果。

8. 只有当采用的机制可扩展、效果随资源持续改善并能被测量时，积累才可能跨过临界点。若方向错误、反馈失真或瓶颈没有解决，重复更多次只是扩大浪费。

9. 生成代码只解决了实现成本的一部分。理解 syscall 和 ISA 才能界定软件与 OS、OS 与硬件的边界；抽象决定项目能否维护和并行推进；测试与运行证据决定生成结果是否真的正确。人需要据此设计、审查和纠偏。
