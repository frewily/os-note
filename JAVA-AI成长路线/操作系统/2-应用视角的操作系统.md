# 第二讲：应用视角的操作系统

> 课程：JYY《操作系统》(2026)  
> 讲义：[应用视角的操作系统](https://jyywiki.cn/OS/2026/lect2.md)  
> 关联：第一讲回答“OS 为什么出现”；本讲回答“一个应用程序如何使用 OS”。

## 一句话主线

**任何应用程序本质上都是一个不断改变自身状态的状态机；它靠普通计算改变自己的状态，靠系统调用（syscall）请求操作系统提供文件、设备、进程和内存等能力。**

```text
应用程序 = 普通计算（自己的变量、栈、内存） + 系统调用（请求 OS 服务）
```

## 1. 先建立最重要的模型：程序是状态机

不要把“状态机”想得很硬件化。对一个 C 程序，可以把它直观理解为：

- **状态**：当前所有变量的值、函数调用栈中的每一层局部变量，以及“下一步要执行哪一行”。
- **初始状态**：从入口函数开始，变量有初始值，下一步从第一条语句执行。
- **状态迁移**：执行当前语句，得到新的变量值、栈或下一条语句位置。

例如：函数调用并不是数学意义上“直接得到一个值”，而是要保存当前函数稍后从何处继续，再为被调用函数创建一层新的栈帧；函数返回时再恢复上一层。这一切都是确定、机械的状态变化。

更精确一点：每个栈帧都可看作保存了该函数的参数、局部变量和它自己的“下一条语句位置”（PC）。执行函数调用时：

1. 调用者的 PC 先前进到调用语句之后，保留“回来后从哪继续”；
2. 在栈顶压入被调函数的新栈帧；
3. 新栈帧的 PC 指向被调函数入口；
4. `return` 时弹出当前栈帧，恢复调用者栈帧，继续执行调用后的语句。

所以，把递归改写为非递归，核心不是寻找某个神秘公式，而是**自己用一个数据结构显式模拟调用栈中的栈帧和 PC**。

> 看不懂递归、函数调用或复杂程序时，不要一次想完整结果。只追踪“当前栈里有什么、当前执行到哪一行、执行这一行后会变成什么”。

### 解释执行与编译执行

| 方式 | 发生什么 | 核心不变 |
| --- | --- | --- |
| 解释执行 | 解释器逐条取语句、解释并执行 | 仍在推进程序状态 |
| 编译执行 | 编译器把高级语言翻译为机器指令，再由 CPU 取指、译码、执行 | 仍在推进程序状态 |

编译器的正确性可以粗略理解为：对相同输入，编译前后的程序应有相同的可观察结果（输出、外部 API 调用，以及是否终止）。因此，最终不会影响外部可观察结果的计算可能被优化掉。

## 2. 程序为什么需要操作系统？

程序的普通指令只能直接改变自己的寄存器、内存等状态；它不能自行：

- 读写任意文件、网络、屏幕或磁盘；
- 创建、终止或等待其他程序；
- 申请更多运行内存；
- 让操作系统把自己正常结束。

这些能力涉及共享资源和安全边界，必须由操作系统统一管理。应用程序要获得服务，就发起**系统调用**。

### `main` 不是机器的第一条指令

在 C 语言的抽象模型里，我们说程序从 `main` 开始；但真实的可执行文件被 OS 加载后，会先从入口地址（常见符号名为 `_start`）开始执行初始化代码。它准备好运行环境，再调用 `main`；`main` 返回后，初始化代码还要请求 OS 正常结束进程。

因此，直接让 `_start` 执行 `return` 并不能“退出程序”：它没有普通调用者可返回，最终会跳到无效位置而崩溃。**进程结束必须由 OS 定义和完成。**

### 系统调用（syscall）

以 Linux/x86-64 为例，程序会：

1. 把“要请求哪项服务”和参数放到约定的位置（通常是寄存器）；
2. 执行 `syscall` 指令；
3. CPU 转而执行操作系统预先指定的代码；
4. 操作系统完成服务并返回结果，或改变/终止该程序。

可把 syscall 直觉地理解为：**程序主动把控制权和更高权限交给 OS**。调用后，OS 才能访问和管理更广的系统资源；它也有权拒绝请求、修改程序状态，或直接结束该进程。

`exit` 是最简单的例子：程序并不是“自己把自己关掉”，而是通过系统调用通知 OS“这个进程可以结束了”。

也可以把一次系统调用看成一份“请求合同”：程序按约定提交调用号和参数；OS 检查参数、权限和资源条件，合法就完成服务并返回结果，非法则返回失败。比如 `read` 成功后，OS 可能把读到的数据写进程序提供的缓冲区，并返回实际读到的字节数。

> 系统调用是本课程最核心的边界：普通计算在程序自身状态内进行；系统调用跨过边界，向 OS 请求能力。

## 3. 应用程序并不神秘

我们平常能感知的是浏览器、IDE、终端、游戏等**进程**，而不是 OS 本身。它们规模相差很大，但底层模型相同：

```text
可执行文件（描述初始状态）
        ↓ 由 OS 加载
进程开始运行：计算 + 系统调用
        ↓
调用 exit / exit_group，进程结束
```

### 可执行文件是什么？

在 Linux 中，常见可执行文件是 ELF。此刻不必研究文件格式细节，只要理解：它保存了让 OS 创建一个程序初始状态所需的信息，例如入口地址、指令序列和初始数据。

所以：**可执行文件不是“正在运行的程序”，而是 OS 用来创建运行中程序初始状态的描述。**

### 常见系统调用按对象分类

| OS 抽象对象 | 常见调用 | 程序获得的能力 |
| --- | --- | --- |
| 进程 | `fork`、`execve`、`exit` | 创建/启动新程序、结束程序 |
| 文件和设备 | `open`、`close`、`read`、`write` | 读写文件、终端、网络连接、设备 |
| 内存 | `mmap`、`brk` | 获得或调整可使用的虚拟内存 |

这也是第一讲“OS 提供对象 + API”的具体化：应用没有直接摆弄硬盘或网卡，而是向 OS 操作对应的抽象对象。

### 应用世界是分层协作的

“浏览器能显示窗口”不代表浏览器直接逐像素控制屏幕。通常是：

```text
应用程序 → 图形库/协议 → 窗口系统或合成器等服务进程 → OS/设备
```

应用把“我要显示什么、收到什么输入”发送给有相应职责的服务进程；后者再统一管理窗口和显示设备。这样多个程序不会同时争抢整块屏幕。U 盘自动挂载、网络管理、定时任务等日常体验也类似，背后常由长期运行的**守护进程（daemon）**监听事件并调用 OS 服务实现。

## 4. 如何看到程序真的在调用 OS？——`strace`

`strace` 会追踪一个程序执行时发生的系统调用。它让“程序 = 计算 + 系统调用”从概念变成可观察的证据。

在 Linux 中可用：

```bash
strace -f gcc a.c
```

- `strace`：显示程序向 OS 发出的调用及返回结果；
- `-f`：连同该程序创建的子进程一起追踪；
- `gcc` 本身会启动多个工具进程，因此能看到 UNIX 小工具组合协作的痕迹。

不需要现在背每一行输出。只要能在输出里认出 `openat`、`read`、`write`、`execve`、`exit_group` 这类名字，就已经抓住了本讲的观察方法。

读长 trace 的方法不是硬看：先把输出保存下来，再围绕一个问题筛选。例如关注 `execve`，可观察 `gcc` 是否启动了汇编器、链接器等其他程序；关注 `unlink`，可观察临时文件何时被删除。**先提出问题，再用工具过滤证据**，比试图理解所有调用更有效。

## 5. 从 API 反推应用如何实现

应用的“魔法”通常都能拆成计算与系统调用的组合：

- 窗口/图形程序：访问显示相关设备或服务，计算出要画的内容，并与其他进程通信；
- 任务管理器：读取 OS 暴露的进程信息；
- 杀毒软件：扫描文件内容，并借助系统提供的调试/监控能力观察进程；
- 编译器：读取源文件、启动其他工具进程、写出目标文件。

因此操作系统的职责不是替应用完成业务逻辑，而是提供足够舒适、安全且可组合的抽象与 API，让应用能在其上构建一切功能。

## 6. 本讲对零硬件基础的最低要求

本讲不需要先学寄存器、汇编或 CPU 电路。先掌握下面三句话即可：

1. 程序运行就是状态不断变化。
2. 普通语句主要改自己的状态；想使用系统资源要请求 OS。
3. `syscall` 是请求 OS 服务的入口，`strace` 能看到这些请求。

后续出现寄存器、栈、入口地址时，再按“它解决什么问题 → 怎么观察 → 必要原理”逐步补充。

## 7. 课后 40 秒复述

第二讲把程序看成状态机：状态包含变量、调用栈和下一条要执行的位置，执行语句就是状态迁移。函数调用会压入新栈帧，返回会弹出它。无论解释执行还是编译成机器指令，本质都是推进状态。真实程序从 `_start` 等入口开始初始化，`main` 返回后仍要由 OS 结束进程。程序的普通计算只能改变自身状态，想读写文件、访问设备、创建进程或退出时，需要通过 `syscall` 把控制权交给操作系统。OS 因而为应用提供进程、文件/设备和内存等对象及 API。任何应用程序都是“计算加系统调用”；`strace` 可以直接观察它和 OS 的交互。

## 8. 自测题

1. 用“状态、初始状态、状态迁移”分别解释一个 C 程序的执行。
2. 为什么函数调用不能只按数学函数理解？栈帧解决了什么问题？
3. 普通指令和系统调用的根本边界是什么？
4. 为什么说可执行文件是“程序初始状态的描述”，而不是运行中的程序？
5. `strace` 能帮助我们确认什么？为什么追踪 `gcc` 时常需要 `-f`？
6. 为什么 `main` 返回不等于进程可以自行结束？

### 参考答案

> 建议先脱稿回答，再展开下面的内容核对；能说出核心因果即可，不必逐字一致。

1. **状态**是程序此刻拥有的全部运行信息，例如全局/局部变量的值、调用栈和每层函数下一条要执行的位置。**初始状态**是 OS 创建并加载程序后，入口代码准备好运行环境的起点；在 C 的抽象模型里可近似为从 `main` 开始。**状态迁移**就是执行当前语句或指令后，变量、栈或下一条执行位置发生变化。

2. 数学函数只强调“输入对应输出”，通常不关心计算先后；C 函数还会按顺序执行，并可能有输出、修改全局状态等副作用。栈帧为每一次函数调用保存参数、局部变量和返回位置，使递归或嵌套调用能在结束后回到正确位置继续执行。

3. 普通指令主要只能改变**当前程序自己的状态**，如寄存器、内存和执行位置；系统调用会把控制权交给 OS，请求跨越程序边界的能力，如文件、设备、进程和内存管理。OS 会检查请求是否合法，并决定完成、拒绝或终止进程。

4. 可执行文件保存了创建程序所需的入口地址、指令和初始数据等信息；OS 加载它后，才根据这些信息创建寄存器、内存、栈等运行状态。文件在磁盘上是静态描述，进程才是正在执行的动态实体。

5. `strace` 记录程序发出的系统调用及其结果，因此能观察程序究竟怎样与 OS 交互，而非只相信源码或经验。`gcc` 编译时往往会创建子进程运行汇编器、链接器等工具；`-f` 能把这些子进程也一起追踪，看到完整调用链。

6. `main` 只是 C 程序的用户代码入口，不是系统层面最初的入口。真实程序在 `_start` 等初始化代码中启动，初始化代码调用 `main`；`main` 返回后仍需要请求 OS 执行 `exit` 来释放进程资源并结束它。若直接从没有调用者的入口 `return`，没有正确的返回地址，程序会进入无效状态甚至崩溃。
