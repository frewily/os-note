# 第一讲：操作系统概述

> 课程：JYY《操作系统》(2026)  
> 讲义：[操作系统概述](https://jyywiki.cn/OS/2026/lect1.md)  
> 目标：先建立全局视角；本讲不要求记住内核细节。

## 一句话主线

**操作系统是硬件和应用程序之间的抽象层：它把难以直接使用、需要被多人共享的硬件资源，变成程序可通过 API 使用的对象和能力。**

学习操作系统，不是为了背一个严格定义，而是为了回答两类问题：

- 程序能做什么？例如创建窗口、访问文件、联网、同时运行多个任务。
- 程序为什么能做到？背后由操作系统提供接口，并协调 CPU、内存和设备。

## 1. 为什么在 AI 时代仍要学操作系统？

AI 可以生成代码、调用工具，但它仍要运行在计算机系统上。操作系统及其应用生态为程序和 Agent 提供了“手和脚”：显示界面、读写文件、发送网络请求、隔离运行环境、调度 CPU/GPU 等。

真正可迁移的能力是：**用抽象分解复杂性，并理解抽象层如何设计和实现。**

> AI 能帮忙写代码，不等于可以不理解系统；越能理解操作系统提供的能力和边界，越能正确地使用、调试和组合程序。

## 2. 什么是操作系统？

### 课程中的狭义操作系统

- 位于**硬件**和**应用程序**之间；
- 对一台（可多处理器）计算机的资源进行抽象和管理；
- 支撑应用程序生态稳定运行。

可以把它先理解为：

```text
应用程序（浏览器、终端、IDE、游戏、Agent……）
                  ↓ 调用 API
操作系统：抽象资源、隔离程序、协调共享、驱动设备
                  ↓
硬件（CPU、内存、磁盘、网卡、显示器……）
```

OSTEP 的说法强调：操作系统让程序更容易运行；让多个程序看起来能同时运行；让它们共享内存、与设备交互。

从程序员视角，它还可以被看成：**一组 API + 一批系统对象**。应用程序通过 API 操作文件、设备、网络连接等对象，也会间接地影响其他正在运行的程序。操作系统需要管理这些程序当前的执行状态，并在资源有限时决定谁能继续运行。

### 不要停在“定义”上

操作系统不是为了增加复杂度，而是因为直接操作硬件很复杂。理解它的正确入口是：

1. 硬件有什么限制和能力？
2. 程序想完成什么？
3. 操作系统在两者之间提供了什么抽象和接口？

## 3. 三条观察主线

理解操作系统的发展，要同时看三件事：

| 线索 | 关注的问题 |
| --- | --- |
| 硬件 | CPU、内存和 I/O 能做什么，有什么瓶颈？ |
| 软件 | 程序规模、语言和应用需求如何增长？ |
| 操作系统 | 为了让软件更好地使用硬件，新增了哪些抽象与管理机制？ |

**操作系统的演化，本质上是硬件能力与软件需求共同推动的。**

## 4. 操作系统如何出现和演化？

| 时期 | 硬件/软件变化 | 操作系统形态 | 要记住的因果 |
| --- | --- | --- | --- |
| 1940s | 计算机刚出现；程序通过接线、纸带、机器指令运行 | **没有操作系统** | 机器只运行极少的程序，程序直接操作硬件，尚不需要额外管理层 |
| 1950s | 计算机昂贵；高级语言和更多 I/O 出现；I/O 比 CPU 慢 | 库函数 + 排队运行的调度代码 | 多人要轮流用同一台机器，算力开始成为服务，OS 概念形成 |
| 1960s–1970s | 集成电路、更大内存、虚拟存储、中断/异常机制 | **资源虚拟化** | 内存、磁盘可做空间复用；CPU 借助中断做时间复用，多个程序得以并发存在 |
| 1970s+ | UNIX 与应用生态发展 | 信号、管道、socket、procfs 等 API/对象 | 稳定的系统接口成为应用软件生态的基础 |

### 1940s：为什么没有操作系统？

- ENIAC 等早期计算机以数字电路实现状态机；重新编程甚至需要重新接线。
- 程序直接用指令操作硬件，连编程语言都尚未成熟。
- 此时“先让一个程序跑起来”已足够困难，管理程序反而是多余的。

### 1950s：为什么开始需要操作系统？

- 计算机极贵，通常一个机构只有一台；写入、提交和切换程序都很费事。
- 多个用户要共享机器，因此出现管理程序排队执行作业的调度代码。
- I/O 远慢于 CPU，硬件出现中断机制，系统需要协调计算与 I/O。
- CTSS 等系统开始把设备、文件、任务等表示为可操作的对象，并提供子程序接口——这正是抽象层的早期形态。

### 1960s–1970s：资源虚拟化是关键转折

操作系统让有限的真实资源呈现为多个程序各自“拥有”的资源：

- **CPU 时间复用**：依靠中断在多个程序间切换，使它们看起来同时执行。
- **内存与磁盘空间复用**：借助 MMU 等硬件机制让多个程序安全地使用内存；“进程”成为重要抽象。

> 资源虚拟化并非凭空制造资源，而是通过切分、复用和隔离，让有限硬件服务更多程序。

课堂中的演化链条更具体地说是：

1. **批处理**：一个程序结束后，操作系统自动装入下一个程序；
2. **多道程序**：内存变大后，可同时装入多个程序。某个程序等待慢速 I/O 时，CPU 不必闲置，可切到另一个程序；
3. **抢占式时间复用**：借助时钟中断，即使当前程序没有主动让出 CPU，操作系统也能在时间片结束时切换出去，之后再恢复它。

这解释了一个直观现象：单线程死循环通常只能持续占用一个核心，并不会让整台多核机器永远失去响应；操作系统仍能通过中断调度其他工作。

### UNIX：现代接口生态的基础

UNIX 将大量系统能力沉淀为程序可组合的接口和对象：信号、管道、`grep`、socket、`procfs` 等。Linux、macOS、BSD、Android 等均可在这条生态脉络中理解。

本课程会从“现代操作系统为应用程序提供哪些 API”切入，而不是以实现内核为主线。

## 5. 本讲涉及的两个思维方式

### 状态机

数字系统在时钟驱动下，离散地更新寄存器状态；程序最终也是处理器执行的一串指令，整个计算过程可理解为状态不断变化。

这条线索后续会连接到：程序执行、上下文切换、进程状态与并发。

可以把本课程的起点记成：**硬件是状态机，程序也是状态机；操作系统负责管理多个正在运行程序的状态，并提供访问系统对象的接口。**

### UNIX Philosophy

讲义用数字电路模拟器演示了命令行工具的协作。核心原则：

- 每个程序只把一件事做好；
- 一个程序的输出应能成为另一个程序的输入；
- 优先使用文本接口。

这也是管道和命令行组合能力强大的原因；对 Agent 而言，明确、可组合的命令行接口也尤其友好。

课堂例子：电路模拟程序只输出 `A=0; B=1; ...` 这样的文本状态，另一个程序读取文本并绘制数码管。两个小程序各自简单，却能经由文本接口组合为一个可视化工具。

### 好抽象层的判断标准

本讲提出的是后续课程要反复观察的设计问题：一个操作系统接口既要能依赖下层硬件实现，又要让上层应用方便、安全地使用，还应能支撑更多程序与工具逐层组合成生态。背术语不如持续追问：**这个 API 抽象了什么？它隐藏了什么复杂性？它让上层多获得了什么能力？**

## 6. 如何学习这门课

- 每次先问“这个 API/机制让程序多获得了什么能力”，再看它如何实现。
- 重视动机和第一性原理，而非孤立背诵边角细节。
- 遇到难以理解的代码，可借助调试器、日志或可视化去观察“当前状态”；先说清状态如何变化，再理解代码。
- 课程实验中可用 AI 协助理解概念、单个 API 或调试思路；不能把完整自然语言需求直接交给 AI 生成后提交。

## 7. 课后 30 秒复述

操作系统是硬件和应用程序之间的抽象层：从程序员视角，它是一组管理程序状态和系统对象的 API。早期机器一次只跑少量程序，程序可以直接操作硬件，所以没有操作系统。随着计算机昂贵、用户增多、I/O 变慢以及软件变复杂，人们需要让多个任务共享机器，于是先有批处理和调度；内存变大后，多个程序可以同时驻留，某个程序等待 I/O 时 CPU 可以执行另一个；再通过中断和时间片实现抢占式切换。操作系统因此把 CPU 做时间复用、把内存和磁盘做空间复用，这就是资源虚拟化。UNIX 又把这些能力稳定为信号、管道、socket 等 API，支撑了现代应用生态。学习操作系统就是理解程序能做什么、为什么能做到，以及这些抽象如何管理复杂性。
