# TCP 拥塞控制：网络塞车了怎么办？

> **模块**：模块五\
> **日期**：2026-06-03\
> **代码**：[Server1.java](file:///Users/frewily/Documents/计算机网络/src/Server1.java)、[Client1.java](file:///Users/frewily/Documents/计算机网络/src/Client1.java)\
> **核心发现**：每个 TCP 段携带 **16332 字节**（lo0 回环接口），远大于 1448（以太网接口）

***

## 一、这一章到底在学什么？

上一章我们发了 13 字节（Hello Server），一个包就装下了。但如果要发 **4MB 数据**呢？

**这一章的核心问题只有两个：**

| 问题             | 你怎么验证的                      | 结论                       |
| -------------- | --------------------------- | ------------------------ |
| ① 4MB 被切成了多少片？ | 在 Wireshark 里看相邻两个包的 Seq 差值 | **每片 16332 字节**，共约 257 片 |
| ② TCP 一次发多少片？  | 看 Stevens 图的阶梯形状            | 窗口逐渐增大，一次发的片数越来越多        |

**拥塞控制 = TCP 的油门控制：根据网络状况决定一次发多少片。**

***

## 二、你的实验

### 2.1 代码改动

把 13 字节的文本消息改成发送 4MB 数据：

**Server1.java（服务端）**

```java
byte[] data = new byte[4 * 1024 * 1024];  // 4MB
OutputStream out = socket.getOutputStream();
out.write(data);
out.flush();
```

**Client1.java（客户端）**

```java
byte[] buf = new byte[4096];
int total = 0;
int len;
while ((len = in.read(buf)) != -1) {
    total += len;
    System.out.println("已接收: " + total / 1024 + " KB");
}
```

### 2.2 核心发现：每个段携带多少字节？

在 Wireshark 中连续点开三个 TCP 段，看它们的 Seq 和 Len：

```
75: Seq=1        Len=16332   → 下一个 Seq 应为 1 + 16332 = 16333 ✅
76: Seq=16333    Len=16332   → 下一个 Seq 应为 16333 + 16332 = 32665 ✅
77: Seq=32665    Len=16332
```

**每个 TCP 段携带了 16332 字节的数据。**

计算一下：

```
4MB = 4 × 1024 × 1024 = 4,194,304 字节
每个段装 16332 字节
需要 4,194,304 ÷ 16332 ≈ 257 个段发完
```

> 之前 13 字节 → 1 个包就发完了\
> 现在 4MB → 被切成 **约 257 个包** 依次发送

**为什么是 16332 而不是通常说的 1448？**

因为 **MSS 取决于底层接口的 MTU**：

| 接口                  | MTU   | 计算方式               | MSS         |
| ------------------- | ----- | ------------------ | ----------- |
| **lo0（回环）**         | 65536 | 65536 - IP头 - TCP头 | ≈ **16332** |
| **en0（Wi-Fi/以太网）**  | 1500  | 1500 - 20 - 32     | ≈ **1448**  |
| **ppp0（VPN/PPPoE）** | 1492  | 1492 - 20 - 32     | ≈ **1452**  |

```
MTU（最大传输单元）→ 底层硬件能承载的最大数据帧
  减去 IP 头部（20 字节）
  减去 TCP 头部（20~60 字节，通常含选项 = 32 字节）
  ─────────────────────────────
MSS（最大段大小）= MTU - IP头 - TCP头
```

你在 `lo0` 上跑的测试，MTU 是 65536，所以能一次装 16332 字节。如果是走 Wi-Fi（`en0`），MSS 才会降到 1448。

### 2.3 Stevens 图：看窗口增长

Wireshark → **Statistics → TCP Stream Graphs → Time-Sequence (Stevens)**

```
序列号 (Seq)
  ▲
  │              ─────
  │         ─────          ← 每一"级台阶"
  │    ─────                   = 一批包同时发出
  │────
  └─────────────────────────→ 时间
```

每一级台阶代表 TCP 一次发了一批包，等收到 ACK 后再发下一批。台阶越来越宽，说明窗口在增长——TCP 在"踢油门"。

> 因为 `127.0.0.1` 是本机回环，没有真正的网络瓶颈，所以看不到丢包减窗。但核心步骤（切片发送 + 窗口调节）已经体现在数据里了。

## 三、理论知识：四个阶段

虽然本机回环看不到丢包，但背后的理论你值得了解——面试常考。

### 阶段 1：慢启动（Slow Start）

TCP 不确定网络带宽时，从小窗口开始试探：

```
第 1 轮： 发   1 个包 → 等 ACK → 窗口 = 2（加倍）
第 2 轮： 发   2 个包 → 等 ACK → 窗口 = 4
第 3 轮： 发   4 个包 → 等 ACK → 窗口 = 8
第 4 轮： 发   8 个包 → 等 ACK → 窗口 = 16
...

指数增长：1 → 2 → 4 → 8 → 16 → 32 → 64 …
```

> 叫"慢"启动是因为起点小，但增长是指数级的，很快。

### 阶段 2：拥塞避免（Congestion Avoidance）

窗口达到阈值后，增速放缓，变为**线性增长**：

```
64 → 65 → 66 → 67 … （每轮只增 1 个 MSS）
```

### 阶段 3：快速重传（Fast Retransmit）

收到 3 个重复的 ACK → 立即重传，不等超时：

```
发送方发了 Seq=1~100
其中 Seq=50 丢了
接收方收到 Seq=51~100 后，每个都回复 "Ack=50"
发送方收到 3 个 "Ack=50" → 立即重传 Seq=50
```

### 阶段 4：快速恢复（Fast Recovery）

```
丢包后：
  1. 拥塞窗口（cwnd）= 减半
  2. 慢启动阈值 = 更新为减半后的值
  3. 回到拥塞避免（线性增长，不再从 1 开始）
```

**有丢包的网络，Stevens 图是锯齿形的**：
`╱╲╱╲╱╲` — 增长 → 丢包减半 → 再增长 → 再丢包减半 …

## 四、一句话总结

> TCP 把大数据切成一段段小片（大小取决于接口 MTU），然后根据网络反馈**控制一次发多少片**——这就是拥塞控制。

***

## 五、和流量控制的对比

| <br />   | 流量控制              | 拥塞控制          |
| -------- | ----------------- | ------------- |
| **控制的谁** | 接收方处理能力           | 网络链路负载        |
| **关键参数** | rwnd（接收窗口）        | cwnd（拥塞窗口）    |
| **控制方式** | 滑动窗口              | 慢启动→拥塞避免→丢包减半 |
| **实际窗口** | 取 min(cwnd, rwnd) | <br />        |

## 六、课后延伸

如果想在真实网络上看到拥塞控制的锯齿图，可以做两件事：

1. **Wireshark 抓** **`en0`（Wi-Fi）访问大文件下载**——观察有没有重传、ACK 重复
2. **配置 macOS 的 dummynet 丢包模拟**（需要 sudo）：

```bash
sudo dnctl pipe 1 config plr 0.1
echo "dummynet on lo0 proto tcp from any to any port 8888 pipe 1" | sudo pfctl -ef -
# 跑完记得恢复：sudo pfctl -f /etc/pf.conf && sudo dnctl -q flush
```
