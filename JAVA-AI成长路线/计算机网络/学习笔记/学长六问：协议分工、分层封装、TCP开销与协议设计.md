## 📋 大纲总览

### 第一问：协议分工 —— HTTP / TCP / IP 各负责什么？
> 📎 关联笔记：[[第一次抓包：我看到了网络请求的样子]] · [[DNS解析：从域名到IP发生了什么]] · [[TCP三次握手：我用Java亲手建立了一条连接]]

**学长原话**：

> "IP 协议通过层层路由找到需要找的那台机器，TCP 协议找到需要传输的端口"
> "IP 协议头有个 IP 字段，每个 IP 对应唯一一台机器，所以 IP 协议是找机器"
> "TCP 协议头有个端口字段，一共 65536 个，所以 TCP 是找端口"
> "应用监听端口，所以两个应用之间就可以通过 TCP 通信"
> "TCP 传输的是数据流，只管传输，不关心自己包着的是什么数据"
> "HTTP 协议才是管实际内容的那个"
> "HTTP 协议头有个长度字段，告诉你这条消息有多长，然后你按照这个长度来拆分信息"

**核心问题**：

- IP 报头的哪个字段负责"找机器"？
- TCP 报头的哪个字段负责"找端口"？
- TCP 收到的是一堆字节流，怎么拆成完整的消息？
- HTTP 解决了什么问题（尤其是 Content-Length）？

**状态**：✅ 已完成

#### ① IP 找机器

**目标 IP** 字段（IP 头中 32 位）负责定位目标主机。路由器根据目标 IP 查路由表，决定下一跳。

**"每个 IP 对应唯一一台机器"的修正**：

- 在局域网内部：每个私有 IP 确实对应唯一一台设备
- 在公网视角：NAT 的存在导致**多个设备共享一个公网 IP**（详见模块八笔记的 NAT 插曲）
- 更准确的说法：**目标 IP 把数据送到正确的网络出口，在局域网内再送到具体机器**

#### ② TCP 找端口

TCP 头的**源端口（16 位）** 和**目标端口（16 位）** 负责标识进程。

- **目标端口为什么是固定的**：由应用层协议约定
  ```
  https://www.baidu.com
         ↓ 协议解析
  HTTPS → 默认目标端口 443
  HTTP  → 默认目标端口 80
  SSH   → 默认目标端口 22
  FTP   → 默认目标端口 21
  ```
  目标端口不是传输层自己决定的，是**应用层协议定死的**，传输层只是执行。
- **源端口为什么随机**：防止同一个机器上多个连接冲突（详见模块八笔记 Q\&A）
- **端口数量 65536 的原因**：TCP 头端口字段占 16 位，2^16 = 65536
- **一句话总结**：IP 把数据送到机器，TCP 把数据送到机器上的具体进程

#### ③ HTTP 管内容

**核心问题：为什么需要 Content-Length？**

TCP 是**流式协议，没有消息边界**。发送方发了两条独立消息，TCP 只负责把字节流按序送达，不关心哪里是一条消息的分界。

学长举的例子：

```
发送 "1+2=3" 然后发送 "-1=2-3"
TCP 收到 → 字节流: 31 32 33 2d 31 3d 32 2d 33
接收端 read() → "1+2=3-1=2-3"
困惑：这是一条 "1+2=3-1=2-3" 还是两条 "1+2=3" + "-1=2-3"？
```

**HTTP 的 Content-Length 解决这个问题**：

```
HTTP 响应头：
Content-Length: 13

接收端先解析 HTTP 头部，知道正文有 13 个字节，然后精确读 13 个字节
```

这就是 **TCP 粘包问题**的典型场景——HTTP 在应用层通过长度字段来划分消息边界。

#### ④ 第一问总结

| 协议   | 核心职责 | 关键字段           | 一句话        |
| ---- | ---- | -------------- | ---------- |
| IP   | 找机器  | 目标 IP          | 把数据送到正确的城市 |
| TCP  | 找端口  | 目标端口           | 把数据送到正确的房间 |
| HTTP | 管内容  | Content-Length | 告诉你怎么拆包裹   |

**分层不可替代**：IP 不关心端口，TCP 不关心内容，HTTP 不关心传输。

#### ⑤ 过渡：三协议的关系与分层协作

**"关系"就是"封装"。** 每一层给上层的数据加一个自己的头，同时隐藏实现细节。

**从发一个 HTTP 请求看分层协作：**

```
生成的 HTTP 报文                    ← HTTP 协议的事
    ↓ TLS 加密（HTTPS 多出来的）    ← TLS 协议的事
添加 TCP 头（端口、SEQ、ACK...）   ← TCP 协议的事
添加 IP 头（源IP、目标IP、TTL...） ← IP 协议的事
添加 MAC 头 + FCS                  ← 以太网协议的事
```

**每一层都不关心上层的细节，只给上层提供服务：**

```
HTTP 依赖 TCP
   → HTTP 不关心怎么传、怎么保证可靠
   → 它只管说"我要发这段内容"，TCP 帮它做可靠传输

TCP 依赖 IP
   → TCP 不关心数据送到哪台机器
   → 它只管说"我要发到这个端口"，IP 帮它找那台机器

IP 依赖链路层（以太网）
   → IP 不关心数据怎么在网线上传
   → 它只管说"目标 IP 是这个"，以太网帮它封装成帧发出去
```

**类比：一封信的旅程**

| 层级   | 角色      | 职责           |
| ---- | ------- | ------------ |
| HTTP | 你写的内容   | "帮我带句话"      |
| TCP  | 快递员承诺回执 | "保证送到，到了告诉你" |
| IP   | 分拣中心看地址 | "发往北京"       |
| 链路层  | 货车司机    | "我只管把件送到下一站" |

**关键理解**：添加 TCP 头**就是** TCP 协议在做的事。协议不是纸面上的文档，它是操作系统内核里实实在在运行的代码。数据每经过一层，就是那层的协议代码在加工它。

### 第二问：分层封装 —— 为什么要一层包一层？在哪拆？
> 📎 关联笔记：[[网络分层模型：一张图串起所有协议]] · [[从输入URL到页面展示：一次完整的网络旅行]]

**学长原话**：

> "可以想想不同协议报文头的作用，为什么要一层包一层"
> "每一层分别起到什么作用？"
> "拿前三层举例（HTTP 应用层，TCP 传输层，IP 网络层），IP 头里包着 TCP 头，TCP 头里包着 HTTP 头"
> "每一个报文头都是在什么地方被拆开的，可以想想"

**核心问题**：

- IP 头是在哪里被拆开的？路由器上？接收端？
- TCP 头是在哪里被拆开的？
- HTTP 头是在哪里被拆开的？
- 为什么路由器不拆 TCP 头？
- "分层"到底带来了什么好处？

**状态**：✅ 已完成

#### ① 路由器拆到什么程度？

路由器只负责**转发**，不负责处理数据内容。收到一个数据帧后：

```
收到：[MAC头 | IP头 | TCP头 | HTTP正文]
        ↑拆掉  ↑读取但不拆
        ↓
查路由表 → 减 TTL → 重算 IP 校验和
        ↓
发出：[新MAC头 | IP头 | TCP头 | HTTP正文]  ← IP 头完好无损地继续走
```

**为什么路由器不拆 TCP 头？**

- 路由器只需要目标 IP 就能决定下一跳，IP 头已经包含了这个信息
- 拆多了是多余的 CPU 开销，路由器每秒要处理数百万个包
- 分层设计的体现：路由器在网络层（IP）工作，不碰传输层（TCP）的事

#### ② 接收端拆包流程

目标机器收到后，从下往上逐层"拆信封"，每层的协议负责读自己那层的头：

```
以太网协议 → 读 MAC 头，验证 FCS，把剩下的交给 IP
IP 协议     → 读 IP 头，检查目标 IP 是否是自己，把剩下的交给 TCP
TCP 协议    → 读 TCP 头，找到端口号，把数据交给对应端口的应用
HTTP 协议   → 读 HTTP 头（含 Content-Length），拿到正文
```

和发送方的封装过程一一对应：

```
发送方封装：            接收方解封装：
HTTP正文                HTTP正文
  ↓ HTTP协议加HTTP头      ↑ HTTP协议读HTTP头
TCP头 + HTTP正文         TCP头 + HTTP正文
  ↓ TCP协议加TCP头         ↑ TCP协议读TCP头
IP头 + TCP段             IP头 + TCP段
  ↓ IP协议加IP头           ↑ IP协议读IP头
MAC头 + IP数据报          MAC头 + IP数据报
  ↓ 以太网加MAC头+FCS       ↑ 以太网读MAC头、验FCS
比特流 → 网线              比特流 ← 网线
```

#### ③ 分层的四个好处

| 好处            | 解释                 | 实例                             |
| ------------- | ------------------ | ------------------------------ |
| **解耦 / 独立演进** | 每层可以独立升级，不影响其他层    | 以太网从 10Mbps → 100Gbps，HTTP 不用改 |
| **各司其职**      | 每层只做自己的事，头不臃肿      | 路由器只看 IP 头，不读 TCP 头            |
| **提供设计问题的框架** | "这是哪一层的事？"本身就是设计语言 | 三次握手是 TCP 的事，HTTP 不管传输         |
| **问题定位**      | 出问题能快速定位到具体层       | 连不上 → 先看 IP 层通不通，再看 TCP 握手     |

### 第三问：三次握手 / 四次挥手 —— 为什么是 TCP 的？
> 📎 关联笔记：[[TCP三次握手：我用Java亲手建立了一条连接]] · [[TCP四次挥手与可靠传输]]

**学长原话**：

> "三次握手四次挥手是什么协议？TCP？"
> "为什么不是 HTTP？"
> "为什么不是 IP？"
> "为什么 TCP 有，UDP 没有？"
> "HTTP 只管内容不管传输，你握手挥手再多次也是那些信息，不会多也不会少"

**核心问题**：

- 为什么三次握手必须是 TCP 的事，HTTP 不能自己做吗？
- IP 是无连接的，它需要握手吗？
- UDP 为什么不需要握手和挥手？
- TCP 握手是在建立什么？（路径？状态？资源？）

**状态**：✅ 已完成

#### ① 为什么不是 IP？

IP 协议**无连接**（connectionless），不维护"连接"的概念，每个 IP 包独立路由转发。IP 是"尽力而为"（best effort），丢了也不管。

IP 没有 SYN/ACK 标志位，没有 SEQ 序列号——它没有做握手的"工具箱"。

**一句话**：IP 不管连接状态，所以不需要握手。

#### ② 为什么不是 HTTP？

HTTP 是**应用层**协议，只关心数据内容（请求什么资源、响应什么类型），不关心传输细节。

**关键证据**：HTTP 头里没有 `SYN`、`ACK` 标志位，没有 `SEQ` 序列号。三次握手的信息全写在 **TCP 头** 里（SYN=1、ACK=1、SEQ=x）。

学长的原话：

> "HTTP 只管内容不管传输，你握手挥手再多次也是那些信息，不会多也不会少"

**本质原因**：HTTP 依赖下层（TCP）帮它做可靠传输。如果硬要让 HTTP 管握手，技术上可以（在 HTTP 头里加字段），但设计上不符合分层原则——谁有 SYN/ACK/SEQ 谁做，那就是 TCP。

**一句话**：HTTP 没有握手的"工具箱"，且依赖 TCP 代劳。

#### ③ 为什么 UDP 没有？

**UDP 哲学**：无连接、不可靠、低延迟。UDP 头只有 8 字节（源端口、目标端口、长度、校验和），没有 SYN/ACK/SEQ，天然不支持握手。

UDP 不是"依赖别人帮它做"，而是**压根不想要连接**。它的设计就是"拿了就发，发了不管"。

| <br /> | TCP              | UDP            |
| ------ | ---------------- | -------------- |
| 连接     | 面向连接，先握手再传       | 无连接，直接发        |
| 可靠性    | 可靠（丢包重传、有序到达）    | 不可靠（丢了就丢了）     |
| 开销     | 重（维护连接状态、序列号、窗口） | 轻（头 8 字节，无状态）  |
| 三次握手   | 有                | 无              |
| 典型场景   | 网页、文件传输、邮件       | 视频通话、DNS 查询、游戏 |

#### ④ 第三问总结

| 协议      | 为什么没有三次握手？                      |
| ------- | ------------------------------- |
| **TCP** | **有。** 面向连接，需要同步初始 SEQ、确认双方在线   |
| IP      | 无连接，不维护连接概念                     |
| HTTP    | 依赖下层 TCP 代劳，自己没有 SYN/ACK/SEQ 字段 |
| UDP     | 设计上就不想要连接，追求轻量和低延迟              |

### 第四问：TCP 开销 —— "重"在哪里？
> 📎 关联笔记：[[TCP三次握手：我用Java亲手建立了一条连接]] · [[TCP拥塞控制：网络塞车了怎么办]]

**学长原话**：

> "TCP 连接状态需要有各种计数器，还有超时重传，滑动窗口，序列号这些东西都需要维护对应数据，所以连接状态的开销通常比较大"

**核心问题**：

- TCP 连接状态具体维护了哪些东西？
- 序列号怎么维护？
- 滑动窗口怎么维护？
- 超时重传的计时器（RTO）怎么维护？
- 这些开销有多大？（内存角度、CPU 角度）
- UDP 为什么没有这些？

**状态**：✅ 已完成

#### ① TCP 为什么要"重"？

TCP 提供**可靠传输**——保证数据不丢、不乱序、不重复，这需要维护大量状态。这些状态存在 OS 内核的 **TCP 控制块（TCB）** 中，每个连接一张"档案卡"。

#### ② 序列号的维护

SEQ / ACK 是**报文头里的字段**（写在包上，Wireshark 可见）；SND 系列变量是**OS 内核内部的 TCB 变量**（你自己看不到）。

| 变量        | 所属方 | 含义                           |
| --------- | --- | ---------------------------- |
| `SND.NXT` | 发送方 | 下一个要发送的 SEQ                  |
| `SND.UNA` | 发送方 | 已发送但还没收到 ACK 的最早 SEQ（未确认的起点） |
| `RCV.NXT` | 接收方 | 期望收到的下一个 SEQ                 |
| `RCV.WND` | 接收方 | 接收窗口大小（还剩多少缓冲区）              |

**发送一个数据包时的流程**：

```
OS 从 TCB 读 SND.NXT → 填入 TCP 头的 SEQ 字段 → 发出
→ 发完后更新 SND.NXT = SND.NXT + 本次发的 Len
```

**示例**（假设初始 SEQ=24321，发 Len=13 的数据）：

```
① 三次握手后：
   客户端：SND.NXT = 24322（SYN 消耗了 1 个序号）
           SND.UNA = 24322

② 客户端发 SEQ=24322, Len=13：
   SND.UNA = 24322（还在等 ACK）
   SND.NXT = 24322 + 13 = 24335

③ 服务器回复 ACK=24335：
   SND.UNA = 24335 ← 确认到了 24335
   SND.NXT = 24335

④ 再发一段 Len=5 的数据：SEQ = 24335
   发完后 SND.NXT = 24340
```

#### ③ 滑动窗口

**为什么需要？** 如果不控制发送速度，发太快会把接收方的缓冲区撑爆。

**核心思想**：允许发送方在收到 ACK 之前连续发多段数据，但总量不能超过上限。

```
接收方在 TCP 头的 Window 字段里告诉发送方："我还有 RCV.WND 这么多空间"

发送方能连续发的上限 = min(对方的 RCV.WND, 自己的拥塞窗口 cwnd)
```

**滑动过程**（假设 SND.UNA=10, SND.NXT=20, RCV.WND=30）：

```
已确认     已发未确认         还能发             还不能发
┌────────┬────────────────┬────────────────┬───────────┐
1       SND.UNA=10     SND.NXT=20     窗口上限=40    100
          ↑              ↑               ↑
      最早未确认      下一个要发       SND.UNA+RCV.WND
                                 还能连续发 20 字节
```

收到 ACK=15 后，窗口右滑：

```
                    ┌── 窗口右移 ──┐
                    ▼              ▼
已确认           已发未确认       能发             还不能发
┌───────────────┬──────────────┬──────────────┬───────────┐
1             SND.UNA=15    SND.NXT=20   窗口上限=45    100
```

**类比**：就像在食堂打饭，窗口里可以同时排着几个人，窗口前的人走了，后面的人就往前挪一步。

#### ④ 超时重传计时器（RTO）

**为什么不能是固定值？** 不同网络的延迟差异巨大：

| 场景    | 典型 RTT       |
| ----- | ------------ |
| 校园网内网 | \~1ms        |
| 家庭宽带  | \~10\~30ms   |
| 跨国    | \~100\~300ms |

如果 RTO 固定设 200ms，内网场景白白浪费时间等待；如果 RTO 设 20ms，跨国连接会频繁误判超时。

**RTO 的计算方式**：

```
OS 记录每个包从发送到收到 ACK 的实际时间 → RTT 采样
RTO = 平均 RTT + 安全余量
    ≈ 平均 RTT × 2（简化）

网络变堵 → RTT 变大 → RTO 自动变大
网络通畅 → RTT 变小 → RTO 自动变小
```

每次收到 ACK 时，OS 会更新这个连接的 RTT 采样值，重新计算 RTO。

#### ⑤ 开销的具体量级

| 维度              | TCP                                                       | UDP                    |
| --------------- | --------------------------------------------------------- | ---------------------- |
| **内存**          | 每连接一张 TCB，约几百字节 \~ 1KB                                    | 无状态，几乎不需要额外内存          |
| **CPU（每收到一个包）** | 查 TCB → 校验 SEQ → 处理乱序 → 更新 RTT → 拥塞控制 → 拷贝到用户空间 **（6 步）** | 校验和 → 直接交给应用 **（快得多）** |

1 万个 TCP 连接 ≈ 几十 MB 内存 + CPU 持续处理 6 道工序；
1 万个 UDP "连接" ≈ 几乎没有额外开销。

#### ⑥ UDP 为什么没有这些？

UDP 的设计哲学是**发完就忘**——不维护连接状态、不备份数据、不排序、不重传、没有窗口和拥塞控制。它的"轻"是设计上主动选择的。

| 特性      | TCP 有                   | UDP 没有 |
| ------- | ----------------------- | ------ |
| 连接状态    | TCB                     | —      |
| SEQ/ACK | SND.NXT / UNA / RCV.NXT | —      |
| 滑动窗口    | RCV.WND 控制流量            | —      |
| 重传计时器   | RTO 动态计算                | —      |
| 拥塞控制    | cwnd / ssthresh 等       | —      |

#### ⑦ 一句话总结

> **TCP 的"重"是为了可靠——要维护连接状态、缓存数据、管理窗口、控制拥塞，每件事都要在 OS 内核里记一张"档案卡"；UDP 的"轻"是因为不管——丢了就丢了，发完就忘，不需要任何状态。**

### 第五问：中间协议 —— TCP 和 UDP 之间有没有"中间地带"？
> 📎 关联笔记：[[TCP三次握手：我用Java亲手建立了一条连接]] · [[TCP拥塞控制：网络塞车了怎么办]]

**学长原话**：

> "进阶可以在 TCP 和 UDP 上思考下，UDP 完全不可靠的话，能不能设计一个在 TCP 和 UDP '中间'的协议，既保证一定的可靠性，又没有 TCP 那么耗费性能？"

**核心问题**：

- 如果让你设计"半可靠"协议，你会保留 TCP 的哪些特性？丢掉哪些？
- 业界有没有现成的例子？（如 QUIC、KCP、RUDP）
- 什么场景需要这种中间协议？（游戏、视频、实时通信）

**状态**：✅ 已完成

#### ① 为什么需要"中间协议"？

TCP 所有特性全保证 → 可靠但"重"（卡顿、延迟大）
UDP 什么都不保证     → 轻但不可靠（可能丢关键数据）

| 场景     | 用 TCP 会怎样      | 用 UDP 会怎样            |
| ------ | -------------- | -------------------- |
| 游戏位置更新 | 丢包卡住等重传 → 卡顿   | 丢包直接跳到新位置 → 响应快但可能瞬移 |
| 充值订单   | 安全到达 ✅         | 可能丢单 ❌               |
| 视频通话   | 卡了也要等重传 → 画面卡死 | 丢几帧不影响体验 ✅           |

实际需求是：**按需选择可靠等级，不是全有或全无。**

#### ② 本质：按需取舍 TCP 特性

中间协议没有统一的"设计公式"。**每个协议选择保留 TCP 的一部分特性、放弃另一部分**，具体取舍取决于目标场景。

| TCP 特性    | 可以放弃吗？ | 放弃后的影响                    |
| --------- | ------ | ------------------------- |
| 数据完整（不丢）  | 部分场景可以 | 状态类数据（位置）丢了没关系，事件类（扣费）不能丢 |
| 顺序保证（不乱序） | 可以     | 先到的先用，不卡顿，但需要应用层处理乱序      |
| 拥塞控制      | 可以     | 发更快，但可能把网络塞爆              |
| 流量控制      | 可以     | 接收方可能撑爆                   |

**两个典型取舍方向：**

**方向一：保留数据完整，放弃顺序保证（不阻塞式重传）**

```
适用场景：事件数据（扣费、攻击判定）——不能丢但可以晚到
做法：先处理后面的数据，丢包重传到再补上
代表：KCP（可配置）
```

**方向二：多流隔离，避免连接级别的队头阻塞**

```
适用场景：一个连接上传多个独立数据流（如浏览器同时加载 HTML 和图片）
做法：每条流内部保持有序，但一条流丢包不影响另一条流
代表：QUIC
```

**对比记忆：**

```
TCP：  一条队列，前面的人卡住 → 后面全停
QUIC： 多条独立队列，一队卡住 → 其他队继续走
KCP：  一条队列但允许插队，前面卡住 → 后面的先走
```

#### ③ 业界代表

| 协议       | 定位           | 解决了 TCP 的什么问题                | 保留了 TCP 的什么         | 放弃了什么          | 典型场景       |
| -------- | ------------ | ---------------------------- | ------------------- | -------------- | ---------- |
| **KCP**  | 可靠 UDP（纯算法层） | TCP 重传慢（等 RTO）、丢包会阻塞后续数据     | 数据完整、重传机制           | 顺序保证（可配置为无序到达） | 游戏（《原神》等）  |
| **QUIC** | HTTP/3 底层协议  | TCP 的**连接级队头阻塞**（一条流丢包阻塞所有流） | 数据完整、有序、拥塞控制等全部可靠特性 | 一个连接只有一个数据流的概念 | HTTP/3、视频流 |
| **RUDP** | 系列协议统称       | 不同实现解决不同问题                   | 因实现而异               | 因实现而异          | 实时通信、语音    |

#### ④ 一句话总结

> **中间协议的思路是在 TCP 的"全都要"和 UDP 的"全不管"之间找到一个平衡点——按需保留可靠特性，丢掉不需要的部分，让协议适配场景而不是场景迁就协议。**

### 第六问：协议设计 —— TCP/UDP 之上怎么设计自己的协议？
> 📎 关联笔记：[[第一次抓包：我看到了网络请求的样子]] · [[计网知识在后端工程中的运用]]

**学长原话**：

> "软件的话一般打交道最底层就是 TCP 或者 UDP，因为拿到的是原始数据，就可以在此之上设计各种协议"
> "HTTP 是一种"
> "微服务模块的 RPC 协议也是一种"
> "Java 的 Netty 就是可以自己设计协议，开发网络应用"
> "很多东西的网络模块都是基于 Netty 开发的"

**核心问题**：

- 什么是"设计协议"？需要定义哪些东西？
- HTTP 是怎么在 TCP 之上设计出来的？
- RPC 协议和 HTTP 有什么不同？
- Netty 是什么？它帮我做了什么？

**状态**：✅ 已完成

#### ① "设计协议"就是在设计三件事

| 要设计什么   | 含义                | 例子：HTTP 的做法                        |
| ------- | ----------------- | ---------------------------------- |
| **定边界** | 怎么从 TCP 流里拆出一条条消息 | Content-Length 头 / 或 \r\n\r\n 分割头部 |
| **定格式** | 消息的每一部分用什么结构      | 请求行 + 头部（key:value）+ 空行 + 正文       |
| **定交互** | 谁先发、谁等谁、什么模式      | 请求-响应模式（客户端请求，服务器响应）               |

#### ② 定边界的三种常见方案

| 方案       | 做法             | 优缺点           |
| -------- | -------------- | ------------- |
| **固定长度** | 每条消息固定 N 字节    | 简单，但浪费空间      |
| **长度前缀** | 前 4 字节表示后面有多长  | 灵活，用得最广       |
| **分隔符**  | 遇到特定字符（如 \n）结束 | 简单，但正文不能包含分隔符 |

#### ③ HTTP 在 TCP 之上的具体设计

HTTP 在 TCP 的流式传输上，用**两种定边界方案**把字节流切成消息：

```
① 分隔符法 → 读头部
   HTTP 头部以 \r\n 分隔每个字段，遇到 \r\n\r\n（空行）表示头部结束

② 长度前缀法 → 读正文
   头部里的 Content-Length 告诉解析器正文有多长，精确读 N 个字节
```

**完整流程：**

```
头部边界（分隔符法）
┌─────────────────────────────────┐
│ HTTP/1.1 200 OK\r\n │
│ Content-Type: text/html\r\n │
│ Content-Length: 13\r\n │
│ \r\n │ ← 遇到空行（\r\n\r\n）→ 头部结束
└─────────────────────────────────┘
正文边界（长度前缀法）
┌─────────────────────────────────┐
│ Hello World! │ ← 读 13 个字节 → 正文结束
└─────────────────────────────────┘
```

你 Java Socket 中用的 `readLine()` 就是分隔符方案的具体例子。

#### ④ RPC 协议和 HTTP 有什么不同？

**RPC（Remote Procedure Call）**：像调用本地方法一样调用远程机器的方法。

```java
// 看起来像本地调用，实际上通过网络发请求
int result = calculatorService.add(3, 5);
```

| <br /> | HTTP                     | RPC（如 Dubbo、gRPC）     |
| ------ | ------------------------ | --------------------- |
| 设计哲学   | "我要这个资源"                 | "帮我执行这个方法"            |
| 设计目标   | 浏览器和服务器之间的资源访问           | 微服务之间的方法调用            |
| 消息格式   | 文本（HTTP/1.1）或二进制（HTTP/2） | 通常二进制（如 Protobuf），更紧凑 |
| 解析效率   | 低（拼 HTTP 字符串、解析 JSON）    | 高（二进制编码，解析速度快）        |
| 边界方案   | Content-Length / chunked | 长度前缀                  |
| 场景     | 对外 API、浏览器               | 内部服务间高频调用             |

#### ⑤ Netty 是什么？

**Netty 是一个 Java 网络编程框架。**

没有 Netty 时，你写 Java Socket 需要自己处理：

```java
ServerSocket serverSocket = new ServerSocket(8888);
Socket socket = serverSocket.accept();     // 等连接
InputStream in = socket.getInputStream();   // 读数据
byte[] buf = new byte[1024];
in.read(buf);                               // 手动处理拆包
// 还要自己开线程池管理多个连接...
```

**Netty 帮你做的事：**

- 管理连接（建立、维护、关闭）
- 处理拆包粘包（你只需要定义"定边界"逻辑）
- 线程模型（IO 多路复用，不用自己开线程池）

你只需要告诉 Netty：**"我的协议长什么样"** + **"收到数据后怎么处理"**。

> 很多 Java RPC 框架（如 Dubbo）底层就是用 Netty 实现的。

#### ⑥ 一句话总结

> **设计协议 = 定边界 + 定格式 + 定交互。HTTP 是这三件事的一个具体实现，RPC 是另一套取舍方案，Netty 是帮你省掉底层 TCP 脏活的框架。**
