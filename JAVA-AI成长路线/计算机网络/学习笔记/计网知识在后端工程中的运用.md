## 二、HTTP 知识 → 后端日常开发

### 2.1 状态码是接口设计的一部分

你学过的 HTTP 状态码，在后端写 API 时每天都在用：

```java
@RestController
public class OrderController {

    @GetMapping("/orders/{id}")
    public ResponseEntity<Order> getOrder(@PathVariable Long id) {
        Order order = orderService.findById(id);
        if (order == null) {
            return ResponseEntity.notFound().build();  // 404
        }
        return ResponseEntity.ok(order);               // 200
    }

    @PostMapping("/orders")
    public ResponseEntity<Order> createOrder(@RequestBody OrderDto dto) {
        // 参数校验失败
        if (dto.getAmount() == null) {
            return ResponseEntity.badRequest().build(); // 400
        }
        Order created = orderService.create(dto);
        return ResponseEntity
            .status(HttpStatus.CREATED)                 // 201
            .body(created);
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleError() {
        return ResponseEntity
            .status(HttpStatus.INTERNAL_SERVER_ERROR)   // 500
            .body(new ErrorResponse("服务器内部错误"));
    }
}
```

### 2.3 Content-Length 与 TCP 粘包

你从学长六问中学到的"TCP 没有消息边界"和"HTTP 用 Content-Length 定边界"，在后端中对应：

```java
// SpringBoot 中处理文件上传
@PostMapping("/upload")
public String upload(@RequestParam("file") MultipartFile file) {
    // Servlet 容器根据 Content-Length + Content-Type: multipart/form-data
    // 自动从 TCP 流中拆分出完整的文件内容
    // 你不需要手动读取 TCP 流、处理边界
    byte[] bytes = file.getBytes();
    return "received " + bytes.length + " bytes";
}
```

背后的完整链条：
```
客户端上传文件 →
    HTTP 头: Content-Length: 1048576
    TCP 层面: 流式传输，可能分成多个 TCP 段到达
    Servlet 容器: 根据 Content-Length 累积读取，直到收齐 1048576 字节
    你的代码: 拿到完整的 MultipartFile 对象
```

### 2.4 HTTPS / TLS 与后端安全

| 后端场景 | 涉及你学过的计网知识 |

| **配置 SSL 证书** | 公钥/私钥对、Certificate 链、CA 信任链 |

## 三、TCP 知识 → 后端性能调优

### 3.1 连接池：为什么需要？配多大？

你在学长六问中学了"TCP 开销重在哪"——每个连接都要维护 TCB、SEQ 变量、窗口、计时器。连接池就是**复用 TCP 连接，避免反复握手的开销**。

```yaml
# HikariCP 连接池配置（SpringBoot 默认）
spring:
  datasource:
    hikari:
      maximum-pool-size: 20      # 最多保持 20 个 TCP 连接到 MySQL
      minimum-idle: 5            # 空闲时保留 5 个
      max-lifetime: 1800000      # 一个连接最多活 30 分钟（避免 TIME_WAIT）
```

**为什么不是越大越好？**

```
TCP 连接数 = 100    →  100 个 TCB × ~1KB = 100KB 内存（不算多）
TCP 连接数 = 10000  →  10000 个 TCB = ~10MB 内存 + 上下文切换开销
    → 线程切换成本飙升 → 实际吞吐量反而下降
```

这就是你学到的"TCP 重"在后端工程中的直接体现：**不是连接越多越快，操作系统维护 TCP 连接是有成本的**。

**对应计网知识**：[[学长六问：协议分工、分层封装、TCP开销与协议设计]] — TCB、连接状态维护

### 3.2 TIME_WAIT：服务器端口耗尽

**真实场景**：高并发短连接下，`netstat` 看到大量 TIME_WAIT：

```bash
$ netstat -an | grep 8080 | grep TIME_WAIT | wc -l
32768   # 端口范围用完了
```

**为什么会出现？**

```
Nginx（主动关闭方）←→ Tomcat（被动关闭方）

请求完成 → Nginx 主动关闭连接 → Nginx 进入 TIME_WAIT
Nginx 端口范围有限（通常 32768~60999，约 2.8 万个）
TIME_WAIT 持续 2MSL（~2 分钟）
高并发下 2 分钟内这 2.8 万个端口用完了 → 新连接无法建立
```

**解决方案你笔记里已经写了：**

```
方案一：用长连接（Nginx upstream keepalive），减少关闭
方案二：调整端口范围（sysctl net.ipv4.ip_local_port_range）
方案三：开启 tcp_tw_reuse（仅适用于客户端角色）
```

面试官问："你的服务器报 `Address already in use` 是什么原因？"——就是你学过的 TIME_WAIT 问题。

**对应计网知识**：[[TCP四次挥手与可靠传输]] — TIME_WAIT 详解

### 3.3 超时重传：接口超时排查

```yaml
# SpringBoot 的 HTTP 客户端超时配置
spring:
  cloud:
    feign:
      client:
        config:
          default:
            connect-timeout: 5000     # TCP 连接超时（对应三次握手阶段）
            read-timeout: 10000       # 等待响应超时（对应数据传输阶段）
```

| 超时类型 | 对应 TCP 阶段 | 超时了你学过的表现 |
|---------|-------------|----------------|
| connectTimeout | 三次握手 | SYN 发出去没回复 → 重试 → 超时报错 |
| readTimeout | 数据传输 | 数据发了，ACK 没回来 → 重传 → 超时报错 |
| 连接池获取超时 | 排队等连接 | 连接池里所有连接都在忙 → 超时 |

### 3.4 拥塞控制：为什么会越调越慢？

**场景**：双十一大促，流量暴涨，接口反而变慢了。

```
正常流量 → 网络畅通 → cwnd 正常增长 → 速度快
    ↓
流量暴增 → 网络拥堵丢包 → TCP 检测到丢包
    ↓
cwnd 减半 → 进入拥塞避免 → 发送速率骤降
    ↓
接口响应变慢 → Tomcat 线程堆积 → 更多超时重传
    ↓
恶性循环 ←
```

你学过的拥塞控制解释了为什么"流量大了反而更慢了"——不是应用代码的问题，是 TCP 在主动踩刹车。

**工程中的对应措施**：
- **限流（Rate Limiting）**：在应用层控制流量，避免把下层网络打爆
- **连接池预热**：提前建立连接，避免慢启动从 1 开始爬坡
- **CDN**：让流量分散到边缘节点，减轻源站链路的拥塞

**对应计网知识**：[[TCP拥塞控制：网络塞车了怎么办]]

### 4.2 服务发现

在微服务架构中，一个服务调用另一个服务：

```
订单服务 ──→ 用户服务（http://user-service:8080）
                  │
                  ↓
            DNS 解析 user-service
                  ↓
            得到 172.16.0.12（Docker 内网 IP）
                  ↓
            TCP 三次握手 → HTTP 请求
```

如果你配置了 Kubernetes，它的 DNS 解析逻辑和你笔记中写的完全一致：
- `service-name.namespace.svc.cluster.local`
- DNS 缓存 → OS DNS 缓存 → DNS 服务器解析

### 4.3 云服务器部署

```
你部署 SpringBoot 项目到 ECS：

ECS 有"公网 IP"和"私有 IP"两个地址（你的 NAT 知识）
    ↓
安全组规则：只开放 80/443 给外网，数据库 3306 只允许私网访问
    ↓
用户访问：域名 → DNS → 公网 IP → NAT → 你的服务器
数据库访问：你的服务器 → 私网 IP → 数据库服务器 → 不走公网
```

## 五、分层模型 → 问题排查

这可能是你笔记中学到的**工程价值最高的思维模型**。

### 5.1 线上接口偶发性超时

```
问题：用户反馈有时候能打开，有时候报 504 Gateway Timeout

没有分层思维的排查：
    猜是代码问题 → 加日志 → 部署 → 观察 → 还是超时
    猜是服务器问题 → 重启 → 好了 → 过一会儿又超时
    循环...

有分层思维的排查：

应用层（你的代码）：
    → 日志里没有抛异常，请求正常处理了 ✅
    
传输层（TCP）：
    → netstat 看到大量 TIME_WAIT
    → 端口耗尽 → 新连接无法建立 ❌
    
网络层（IP）：
    → ping 正常，网络是通的 ✅

结论：TIME_WAIT 导致端口耗尽 → 改为长连接解决
```

### 5.2 请求到一半断了

```
问题：用户上传文件到 50% 断了

应用层（HTTP）：
    → 没有收到完整的 POST 请求体 ✅
    
传输层（TCP）：
    → 抓到 RST 包，连接被强制复位 ❌
    
排查方向：
    → Nginx 的 client_max_body_size 设小了？
    → 负载均衡的超时时间太短？
    → 客户端网络不稳定？
```

### 5.3 通用排查路线图

```
线上出问题
    │
    ▼
应用层（HTTP） ← 先看 Nginx/Tomcat 日志，确认是不是业务逻辑错
    │ 正常？
    ▼
传输层（TCP）  ← netstat 看连接状态、TIME_WAIT、重传统计
    │ 正常？
    ▼
网络层（IP）   ← ping/traceroute 看网络通不通
    │ 正常？
    ▼
链路层/物理层  ← 网线、Wi-Fi、云厂商物理机（最不可能但知道有这一层）
```

## 六、综合案例：一个接口的生命周期

一个请求从客户端到后端服务再到数据库返回，你学的每一层知识都在起作用：

```
客户端（浏览器/App）
    │
    ① DNS 解析 api.your.com → 120.55.12.34
        └─ 你学过的：迭代查询、DNS 缓存、A 记录
    
    │
    ② TCP 三次握手 → 连接建立
        └─ 你学过的：SYN/SYN-ACK/ACK、SEQ 随机化
    
    │
    ③ TLS 握手 → 加密通道建立
        └─ 你学过的：Client Hello、Certificate、密钥交换
    
    │
    ④ HTTP 请求 → 经过 CDN → Nginx → SpringBoot
        └─ 你学过的：请求行/头/体、Content-Length、缓存策略
    
    │
    ⑤ SpringBoot 处理 → 从连接池取一个 TCP 连接到数据库
        └─ 你学过的：连接池复用、TCP 开销、端口
    
    │
    ⑥ 数据库查询 → 返回数据 → 响应走同样的链路返回
        └─ 你学过的：分层封装/解封装
    
    │
    ⑦ 请求处理完 → 连接归池或关闭
        └─ 你学过的：四次挥手、TIME_WAIT、长连接 vs 短连接
```

**这整条链路中，你在已有笔记中已经学过了 90% 以上。**
