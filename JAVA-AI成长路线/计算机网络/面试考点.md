## 一、网络分层与协议分工

### 1. HTTP、TCP、IP、以太网分别负责什么？

- **HTTP**：应用层协议，规定请求和响应的格式与语义，负责表达“要访问什么、提交什么数据、服务器返回什么结果”。
- **TCP**：传输层协议，在两个应用之间提供可靠、有序的字节流传输，并通过端口号区分具体应用。
- **IP**：网络层协议，使用 IP 地址标识主机，并负责让数据包跨越多个网络到达目标主机。
- **以太网**：链路层技术，在局部网络中传输数据帧，使用 MAC 地址识别网卡和当前链路上的下一跳设备。

面试简答：

> HTTP 管内容，TCP 管可靠传输，IP 管跨网络找主机，以太网管局部网络发帧。

### 2. 数据是怎样逐层封装的？

发送端通常经历以下过程：

```text
HTTP 数据
  ↓ TCP 添加 TCP 首部
TCP 段（Segment）
  ↓ IP 添加 IP 首部
IP 包/数据报（Packet / Datagram）
  ↓ 以太网添加帧头和帧尾
以太网帧（Frame）
```

TCP 首部常见信息：

- 源端口、目标端口；
- 序列号、确认号；
- SYN、ACK、FIN 等控制标志；
- 接收窗口；
- 校验和。

IP 首部的核心地址是源 IP 和目标 IP。链路层帧的核心地址是源 MAC 和目标 MAC。

### 3. 最终目标 IP 与下一跳 MAC 的区别

访问外网时：

- IP 首部中的目标 IP 通常仍然是远程服务器的 IP；
- 当前以太网帧中的目标 MAC 通常是默认网关的 MAC。

默认网关收到当前链路上的帧后，会根据目标 IP 继续转发。数据每经过一个局部网络，链路层的 MAC 地址可能重新变化；IP 层的最终目标通常不变。

如果目标主机与发送主机处于同一局域网，发送方通常会通过 ARP 获取目标主机的 MAC；如果目标主机在外网，发送方通常获取的是默认网关的 MAC。

## 二、TCP 端口与连接标识

### 1. TCP 如何区分同一台主机上的不同应用？

TCP 使用端口号区分具体应用。通信双方分别有源端口和目标端口：

- IP 地址：定位主机；
- 端口号：定位主机上的网络应用。

一条 TCP 连接通常可以由四元组标识：

```text
源 IP + 源端口 + 目标 IP + 目标端口
```

常见端口约定：HTTP 通常使用 `80`，HTTPS 通常使用 `443`。

## 三、HTTP 状态码

### 1. 常见状态码

| 状态码 | 含义 | 常见解释 |
| --- | --- | --- |
| `200 OK` | 成功 | 服务器成功处理请求并返回正常响应 |
| `301 Moved Permanently` | 永久重定向 | 资源已经永久迁移，通常通过 `Location` 告知新地址 |
| `404 Not Found` | 资源不存在 | 服务器找不到请求的路径或资源 |
| `500 Internal Server Error` | 服务器内部错误 | 服务器处理请求时发生未妥善处理的异常或内部故障 |

### 2. 404 是否代表 TCP 连接失败？

不是。

通常流程是：

1. TCP 连接建立；
2. 客户端发送 HTTP 请求；
3. HTTP 服务端找不到对应资源；
4. 服务端返回 `404` 响应。

因此，收到 HTTP 状态码通常说明请求已经到达某个 HTTP 服务并获得了应用层响应。若 TCP 连接失败，通常收不到 HTTP 状态码，而会出现连接超时、连接被拒绝或网络不可达等错误。

## 四、与 Agent 项目的联系

前端请求 Java 后端时，可以这样解释：


1. 前端在 HTTP 请求中表达接口路径、参数和请求体；
2. TCP 通过端口把数据交给目标 Java 服务，并负责可靠传输；
3. IP 负责把数据包送到目标主机；
4. 如果 Java 服务位于外网，当前局域网帧先发送给默认网关；
5. Java 服务处理请求后，再沿相反方向返回 HTTP 响应。

这里的“理解并能复述”不等于已经完成抓包验证。后续需要结合 Wireshark 或实际接口请求，核对 HTTP、TCP、IP 字段在真实报文中的表现。

## 五、TCP 序列号、确认与可靠传输

### 1. 序列号的作用

TCP 序列号 `seq` 标记 TCP 字节流中本段数据第一个字节的位置。数据段携带序列号和长度后，接收方可以按字节位置排序、重组数据，并识别缺口或重复数据。

例如，数据从 `seq=1000` 开始，长度为 500 字节，则这段数据覆盖 `1000–1499`，后续连续数据从 1500 开始。

### 2. ACK 的含义与累计确认

确认号 `ack` 通常表示接收方**下一个期待的字节序号**。因此 ACK 确认的是从此前位置开始连续收到的数据，不是简单确认最新抵达的段。

例子：

- 已连续收到 `1000–1499`，接下来期待 1500，因此回 `ack=1500`。
- 若 `seq=2000` 的数据先到，但 `1500–1999` 缺失，累计 ACK 仍为 `ack=1500`；实现可缓存乱序数据并发送重复 ACK。
- 缺失数据补齐，且数据连续覆盖到 `2499` 后，ACK 前进到 `ack=2500`。

区分标志位与字段：`ACK=1` 表示确认号字段有效；`ack=2500` 表示具体确认位置。

### 3. TCP 如何应对损坏和丢包

- **校验和**：检测报文损坏。校验失败的段通常被接收方丢弃，不交付应用层；接收方一般不会单独发送“请重传”消息，发送方因未收到覆盖该数据的 ACK 而超时重传，或在符合条件时根据重复 ACK 快速重传。
- **确认应答**：接收方用 ACK 报告连续接收进度。
- **超时重传**：发送方等待确认超时后，重新发送未确认数据。
- **快速重传**：接收方发现序号缺口时，累计 ACK 仍指向下一个期待的字节序号；后续乱序数据可能被缓存。发送方收到多个相同的重复 ACK，可在超时前推断缺口段可能丢失并提前重传。经典 TCP Reno 常以 3 个重复 ACK 触发快速重传；具体实现与算法可能不同。
- **序列号**：支持排序、重组、检测重复数据和定位缺口。

### 4. 滑动窗口、流量控制与拥塞控制

滑动窗口允许多个未确认数据段同时在途；收到确认后，发送窗口向前移动，减少每段都停下来等 ACK 的空闲时间。

- **接收窗口 `rwnd`**：接收方通告的接收能力，用于流量控制，避免接收缓冲区溢出。
- **拥塞窗口 `cwnd`**：由发送方维护的网络拥塞估计，用于限制在途数据量；它不是路由器直接通告的窗口。发送方根据确认、丢包和延迟等网络反馈调整它。
- **流量控制**关注接收方是否接得住；**拥塞控制**关注路径中的链路和路由器队列是否过载。队列排队会增加延迟，队列满时会丢包。
- 发送方允许的在途数据量会同时受到 `rwnd` 与 `cwnd` 限制，常用直觉可记为受两者中较小值约束。

## 六、TCP TIME-WAIT 与 2MSL

主动关闭方收到对端 FIN 并发送最后 ACK 后，进入 TIME-WAIT。等待 2MSL 主要有两个原因：

1. 若最后 ACK 丢失，对端会重传 FIN；主动关闭方仍处于 TIME-WAIT，可以再次发送 ACK。
2. 给旧连接中滞留的报文留出过期时间，降低旧报文干扰后续复用相同连接四元组的新连接的风险。

TIME-WAIT 的连接端点仍保留状态以处理上述情况；不能简单概括成“只能接收、不能发送”。
