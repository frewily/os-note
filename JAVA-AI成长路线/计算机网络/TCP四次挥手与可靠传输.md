# TCP 四次挥手与可靠传输

> **模块**：模块四 · 断开连接也有这么多讲究\
> **日期**：2026-06-03\
> **基于**：模块三的同一份抓包数据（回环地址 127.0.0.1:8888）

## 一、回顾抓包结果

在模块三的 10 条报文中，后 4 条属于四次挥手：

```
No.  Time         Source→Dest         Info
 ⑥  32.188954    65082 → 8888        [FIN, ACK]  Seq=14  Ack=1   ← 客户端发起关闭
 ⑦  32.188967    8888  → 65082       [ACK]       Seq=1   Ack=15  ← 服务器确认
 ⑧  32.189213    8888  → 65082       [FIN, ACK]  Seq=1   Ack=15  ← 服务器也关闭
 ⑨  32.189228    65082 → 8888        [ACK]       Seq=15  Ack=2   ← 客户端最终确认
```

- 各步间隔仅 13\~246 微秒（因为 127.0.0.1 回环，延时极小）
- 如果是远程服务器，挥手耗时会更明显

## 二、四次挥手详解

### 2.1 完整流程

```
主动关闭方（客户端）              被动关闭方（服务器）
      │                                  │
      │──── ① FIN ──────────────────→   │  ① "我说完了"
      │     Seq=14, Ack=1                │
      │                                  │
      │←── ② ACK ───────────────────    │  ② "收到了，等我也处理完"
      │     Seq=1,  Ack=15               │
      │                                  │
      │            ... 半关闭状态 ...     │  服务器还可以发数据
      │                                  │
      │←── ③ FIN ───────────────────    │  ③ "我也说完了"
      │     Seq=1,  Ack=15               │
      │                                  │
      │──── ④ ACK ──────────────────→   │  ④ "收到，关了吧"
      │     Seq=15, Ack=2                │
      │                                  │
      │     客户端进入 TIME_WAIT          │
      │     （等待 2MSL = 约 2 分钟）      │
```

### 2.2 四个步骤拆解

| 步骤 | 标志位     | 谁→谁     | 含义                  |
| -- | ------- | ------- | ------------------- |
| ①  | **FIN** | 客户端→服务器 | 客户端说"我没数据要发了，但我还能收" |
| ②  | **ACK** | 服务器→客户端 | 服务器说"收到了，你先等着"      |
| ③  | **FIN** | 服务器→客户端 | 服务器说"我也没数据要发了"      |
| ④  | **ACK** | 客户端→服务器 | 客户端说"收到，彻底关闭"       |

### 2.3 为什么是四次而不是三次？

因为 TCP 是**全双工**的——双方可以独立收发数据。

- 客户端关闭时（①），只是告诉服务器"我不发了"，但**还可以收**
- 服务器可能还有数据要发，所以先回复 ACK（②）表示"知道了"，等发完数据再发自己的 FIN（③）
- 如果服务器也没有数据要发了，②和③可能合并成一个包，变成**三次挥手**

> 你的这次抓包中②和③没有合并，是标准的四次挥手。

## 三、半关闭状态

```
① FIN → ③ FIN 之间的时间，称为"半关闭状态"
    客户端：不能发了，但还能收
    服务器：还能发，但知道客户端要关了
```

你的程序里 `socket.close()` 直接关闭了整个 socket（读写都关），但 TCP 协议层面，①到③之间的服务器实际上还可以发送数据。

### 追问：半关闭后客户端怎么还能发 ACK？

**关键区分：应用层数据 vs 协议控制报文**

```
客户端调 socket.close() 之后：

  应用层（你的 Java 代码）   ⟵   不能再 write() 业务数据了
      ↓
  传输层（操作系统内核）      ⟵   照常运行，能发 ACK 等控制包
```

第④步的 ACK 不是你的代码发的——是**操作系统 TCP 协议栈自动回复的**。

| 发送类型     | 例子                        | 半关闭后还能发？     |
| -------- | ------------------------- | ------------ |
| **应用数据** | `writer.println("Hello")` | ❌ 不能         |
| **协议控制** | ACK / FIN / RST           | ✅ 能（协议栈自动处理） |

> 协议栈就像底层信使——你把门关了（`close()`），说"我不寄包裹了"（不发业务数据），但信使还在外面跑，帮你收发确认回执（ACK/FIN）。

## 四、TIME\_WAIT 状态（关键）

### 4.1 什么时候进入？

第④步客户端发送最后一个 ACK 后，客户端进入 TIME\_WAIT 状态。

### 4.2 持续多久？

```
TIME_WAIT 时长 = 2 × MSL（Maximum Segment Lifetime）
MSL = 报文在网络上的最大生存时间
标准 MSL = 60 秒
→ TIME_WAIT ≈ 2 分钟
```

### 4.3 为什么需要 TIME\_WAIT？

**原因一：防止最后一个 ACK 丢失**

```
不用 TIME_WAIT：
  ④ 的 ACK 丢了
  服务器没收到 → 以为③的 FIN 客户端没收到 → 重发 FIN
  但客户端已经关端口了 → 没人理 → 服务器报错 ❌

用了 TIME_WAIT：
  ACK 丢了 → 服务器重发 FIN
  客户端还在监听 → 重新回复 ACK → 正常关闭 ✅
```

**原因二：防止旧连接的数据干扰新连接**

```
同一个端口（65082）关闭后立即被新连接使用
→ 可能收到上一个连接的"迷路"数据包
→ 数据错乱 ❌

TIME_WAIT 等 2 分钟
→ 足够网络上所有迷路包死亡
→ 安全重用 ✅
```

### 4.4 查看系统中的 TIME\_WAIT

```bash
netstat -an | grep TIME_WAIT
```

高并发服务器（Tomcat、Nginx）上 TIME\_WAIT 积累过多会耗尽端口资源，是常见的性能调优场景。

## 五、TCP 可靠传输机制（总结）

通过前三个模块，你已经见识到了 TCP 确保可靠传输的几种手段：

| 机制             | 作用               | 你抓到的证据                |
| -------------- | ---------------- | --------------------- |
| **序列号（SEQ）**   | 每个字节都有编号，保证不乱序   | Seq 从 1 → 14 → 15 递增  |
| **确认应答（ACK）**  | 接收方告诉发送方"我收到了多少" | Ack=14 表示前 13 字节已收齐   |
| **握手建立连接**     | 确保双方都在线、愿意通信     | SYN → SYN-ACK → ACK   |
| **挥手关闭连接**     | 确保双方都同意关闭，数据不丢   | FIN → ACK → FIN → ACK |
| **TIME\_WAIT** | 保证最后一个 ACK 可靠送达  | —                     |

***

## 六、关键领悟

1. **全双工通信** — 两边各自独立收发，关闭也要各自独立关
2. **四次挥手 ≠ 必须四次** — 服务器可以在收到 FIN 后立即回复 FIN+ACK，变成三次
3. **TIME\_WAIT 不是浪费** — 是协议可靠性的保障机制
4. **本机回环（127.0.0.1）挥手极快** — 微秒级别，远程连接才看得出延时
