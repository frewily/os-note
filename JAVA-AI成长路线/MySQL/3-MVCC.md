# MVCC（多版本并发控制）

---

## 核心

MVCC 让**读不加锁**——读操作不会阻塞写操作，写操作也不会阻塞读操作。

---

## 为什么需要 MVCC

如果没有 MVCC，并发事务只能靠锁来隔离：

```
事务 A 写数据 → 锁住 → 事务 B 读数据 → 等待 → 事务 A 释放锁 → 事务 B 才能读
```

这就是串行化隔离级别——性能极差。

MVCC 的做法是：**每行数据保存多个历史版本，事务只看到自己"该看到"的版本**。读操作不需要等待写操作释放锁。

---

## 核心机制

### 隐藏字段

InnoDB 每行数据有三个隐藏字段：

```
| 数据字段 | DB_TRX_ID | DB_ROLL_PTR | ... |
|---------|-----------|-------------|-----|
| name='张三' | 事务ID=100 | 指向上一个版本 |
```

| 隐藏字段 | 作用 |
|---------|------|
| `DB_TRX_ID` | 最后修改该行的事务 ID |
| `DB_ROLL_PTR` | 回滚指针，指向 undo log 中的上一个版本 |

### undo log 版本链

每次修改数据时，旧版本被写入 undo log，通过 `DB_ROLL_PTR` 串联成链：

```
当前版本(name='张三', trx_id=103) → 旧版本(name='李四', trx_id=102) → 更旧(name='王五', trx_id=101)
```

### ReadView（读视图）

当事务执行 SELECT 时，生成一个 ReadView，决定当前事务能看到版本链中的哪个版本：

| ReadView 内容 | 含义 |
|--------------|------|
| `m_ids` | 正在活跃（未提交）的事务 ID 列表 |
| `min_trx_id` | 活跃事务中的最小 ID |
| `max_trx_id` | 当前已出现过的事务 ID 最大值 + 1 |

**判断规则**：遍历版本链，对每个版本的 `trx_id`：
- 等于当前事务 ID → 可见（自己的修改当然能看）
- 小于 `min_trx_id` → 可见（该事务已提交）
- 在 `m_ids` 中（未提交）→ 不可见，继续往旧版本找
- 大于等于 `max_trx_id` → 不可见，该事务在当前 ReadView 之后才开启

---

## RC vs RR 的区别

| | RC（读已提交） | RR（可重复读，MySQL 默认） |
|--|-------------|------------------------|
| ReadView 生成时机 | 每次 SELECT 都生成新的 | 事务中第一次 SELECT 生成，之后复用 |
| 效果 | 能读到其他事务已提交的最新数据 | 整个事务中读到同一份快照 |
| 不可重复读 | ❌ 可能发生 | ✅ 不会发生 |

**RR 解决不可重复读的原理**：因为 ReadView 在整个事务中不变，后续 SELECT 看到的版本链起点始终与第一次 SELECT 时一致。

---

## 快照读 vs 当前读

```sql
-- 快照读（不加锁，读历史版本）
SELECT * FROM users WHERE id = 1;

-- 当前读（加锁，读最新已提交版本）
SELECT * FROM users WHERE id = 1 FOR UPDATE;    -- 排他锁
SELECT * FROM users WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁
UPDATE users SET name = '新名字' WHERE id = 1;   -- 更新操作也是当前读
DELETE FROM users WHERE id = 1;                  -- 删除操作也是当前读
```

MVCC 的"不加锁"只针对快照读。当前读仍然会加锁。

---

## 项目关联

| 场景 | 说明 |
|------|------|
| **高并发读取** | MVCC 保证 SELECT 不会被 UPDATE 阻塞，读多写少的场景性能好 |
| **报表统计** | 长事务中多次查询同一范围，RR 级别保证结果一致（ReadView 不变） |
| **`SELECT ... FOR UPDATE`** | 需要真正锁定数据时（如扣库存），走当前读，不走 MVCC |
