# 锁机制

---

## 核心

MySQL 用锁来控制并发写入——锁的粒度越细，并发度越高，但也越复杂。

---

## 行锁

InnoDB 默认使用行锁，只锁住涉及的行，其他行不受影响。

```sql
-- 事务 A
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- 只锁住了 id=1 这一行
-- 其他用户修改 id=2 不受影响

-- 事务 B（可以执行，不阻塞）
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

**行锁的实现依赖索引**：
- 如果 WHERE 条件走了索引 → 锁住索引对应的行
- **如果 WHERE 条件没走索引 → 行锁升级为表锁**（全表扫描时 InnoDB 必须锁所有行）

**vibe coding 视角**：看到 `UPDATE ... WHERE` 没走索引的 SQL 时，不仅查询慢，还会锁全表。

---

## 间隙锁

间隙锁锁住的是**行与行之间的间隙**，防止其他事务在这个间隙中插入新数据。

```sql
-- 假设 users 表 id 有 1, 3, 5, 7
-- 事务 A
BEGIN;
SELECT * FROM users WHERE id BETWEEN 3 AND 5 FOR UPDATE;
-- 锁住了 id=3、id=5 这两行，以及它们之间的间隙

-- 事务 B（被阻塞）
INSERT INTO users (id, name) VALUES (4, '新用户');
-- id=4 在 (3, 5) 的间隙中，被间隙锁挡住
```

**间隙锁只在 RR 隔离级别下生效**，RC 级别没有间隙锁。

**作用**：防止幻读——如果没有间隙锁，事务 A 两次查询同一范围，第二次可能多出其他事务插入的新数据。

---

## 临键锁

临键锁 = **行锁 + 间隙锁**，InnoDB RR 级别默认的锁机制。

```
          间隙锁        行锁        间隙锁        行锁        间隙锁
        ────── (─∞, 1) ─ [1] ─ (1, 3) ─ [3] ─ (3, 5) ─ ...
```

```sql
-- 事务 A
SELECT * FROM users WHERE id = 5 FOR UPDATE;
-- 实际上锁住的是 (3, 5] 这个区间——间隙锁 (3,5) 加上行锁 [5]
```

**实际影响**：如果你在 RR 级别下给一个不存在的行加锁（如 `id=100` 不存在），会锁住一个范围，阻止其他事务在这个范围内插入数据，可能导致意外的阻塞。

---

## 死锁

两个事务互相等待对方释放锁：

```
事务 A：锁住 id=1 → 等待 id=2 的锁
事务 B：锁住 id=2 → 等待 id=1 的锁
→ 互相等待，死锁
```

InnoDB 会自动检测死锁，选择回滚其中一个事务（通常回滚影响较小的那个）。

**如何避免死锁**：
- 多个事务按**相同顺序**访问资源（都先 id=1 再 id=2）
- 缩短事务时间——锁持有越短，冲突概率越低

---

## 锁的行为速查

| 操作 | 加什么锁 |
|------|---------|
| `SELECT ... FROM` | 不加锁（快照读，走 MVCC） |
| `SELECT ... FOR UPDATE` | 行锁（当前读） |
| `UPDATE ... WHERE id = ?` | 行锁（当前读） |
| `DELETE FROM ... WHERE id = ?` | 行锁（当前读） |
| `INSERT INTO ...` | 行锁（插入意向锁） |
| WHERE 没走索引的写操作 | 表锁（实际是锁所有行） |

---

## 项目关联

| 场景 | 说明 |
|------|------|
| **扣库存/扣余额** | `UPDATE ... WHERE id = ?` 走主键索引，行锁不会阻塞其他商品的写入 |
| **高并发下单** | 按相同顺序操作（如先扣余额再扣库存），避免死锁 |
| **批量更新** | 长事务中批量更新多行，锁范围大，尽量拆成小批次 |
| **统计查询加锁** | `SELECT ... FOR UPDATE` 在 RR 下会有间隙锁，注意范围 |
