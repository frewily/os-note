# 索引

---

## 核心

索引是加速查询的数据结构，类似书的目录——没有索引就是逐页翻（全表扫描），有索引就能直接翻到目标页。

---

## 索引的底层结构

MySQL InnoDB 使用 **B+Tree** 作为索引结构：

- 非叶子节点只存 key，不存数据 → 能存更多 key → 树更矮
- 叶子节点存完整数据（聚簇索引）或主键值（二级索引）
- 叶子节点用双向链表连接 → 范围查询直接走链表，不需要回树

**为什么是 B+Tree 而不是二叉树**：二叉树层数深，每次加载一层就是一次磁盘 IO。B+Tree 一个节点能存上千个 key，3~4 层就能存上亿数据，查询只需 3~4 次 IO。

---

## 聚簇索引 vs 二级索引

```sql
-- InnoDB 默认主键就是聚簇索引
CREATE TABLE users (
    id    BIGINT PRIMARY KEY,        -- 聚簇索引：叶子节点存整行数据
    name  VARCHAR(50),
    email VARCHAR(100)
);

-- 普通索引就是二级索引
CREATE INDEX idx_name ON users(name);  -- 叶子节点只存 id，查完整数据需要回表
```

| | 聚簇索引 | 二级索引（非聚簇索引） |
|--|---------|-------------------|
| 叶子节点存什么 | 完整行数据 | 主键值 |
| 每张表有几个 | 1 个 | 多个 |
| 查询流程 | 直接找到数据 | 先找到主键，再回表查 |
| 覆盖索引 | 本身就是 | 如果查询字段都在索引里，不需要回表 |

**vibe coding 视角**：`SELECT *` 查二级索引字段时会回表（多一次 IO）。如果只查索引中已有的字段（如 `SELECT name` 且 name 上有索引），不需要回表——这叫**覆盖索引**，AI 生成的查询可以留意这一点。

## 最左前缀法则

```sql
-- 联合索引 (a, b, c)
CREATE INDEX idx_a_b_c ON users (a, b, c);

-- 走索引
WHERE a = 1                          -- ✅
WHERE a = 1 AND b = 2                -- ✅
WHERE a = 1 AND b = 2 AND c = 3      -- ✅
WHERE a = 1 AND c = 3                -- ✅ a 走索引，c 不走（跳过了 b）
WHERE b = 2                          -- ❌ 没从 a 开始，不走索引

-- 排序也能用联合索引
ORDER BY a, b                        -- ✅
ORDER BY b, a                        -- ❌ 顺序不对
```

**本质**：联合索引按 (a, b, c) 顺序排序存储。查询条件必须从最左边开始匹配，跳过了某一列，后面的列无法使用索引。

---

## 什么时候需要索引

```sql
-- 需要索引的情况
WHERE name = '张三'                  -- 经常作为查询条件
ORDER BY created_at                  -- 经常排序
JOIN ON u.id = o.user_id            -- JOIN 关联字段
```

```sql
-- 不需要索引的情况
WHERE gender = '男'                  -- 区分度低（几乎一半一半）
表数据量很小（几百行）                -- 全表扫描比走索引还快
频繁写入的字段                        -- 索引维护有成本
```

## EXPLAIN——看查询是否命中索引

```sql
EXPLAIN SELECT * FROM users WHERE email = 'test@test.com';
```

输出中重点关注：

| 字段 | 要看的 |
|------|--------|
| `type` | `ALL`（全表扫描，危险） vs `ref`/`range`（走索引了） |
| `key` | 实际使用的索引名，`NULL` = 没走索引 |
| `rows` | 扫描了多少行，越小越好 |
| `Extra` | `Using filesort`（没用到索引排序）、`Using index`（覆盖索引） |

**vibe coding 视角**：AI 生成的 SQL 如果怀疑有性能问题，加个 `EXPLAIN` 看是不是 `type: ALL`。是的话考虑加索引或改写查询。

## 项目关联

| 场景 | 说明 |
|------|------|
| **用户登录** | `WHERE email = ?` — email 字段应有唯一索引 |
| **消息列表分页** | `ORDER BY created_at DESC LIMIT 20` — created_at 加索引避免文件排序 |
| **JOIN 查询** | 关联字段（如 user_id）应在两张表上都建索引 |
| **状态统计** | `WHERE status = ?` — 如果 status 区分度低，索引不一定有效 |
