# 过期删除策略

---

## 核心

Redis 不会实时扫描所有 key 检查是否过期——它用"定期删除 + 惰性删除"配合，在性能和准确性之间取得平衡。

---

## 两种策略

### 定期删除

Redis 每隔 100ms 随机抽取一部分设置了过期时间的 key，检查并删除已过期的。

```
每 100ms：
  ① 从设置了过期时间的 key 中随机抽 20 个
  ② 检查这 20 个中有没有过期的
  ③ 删除过期的
  ④ 如果超过 25% 过期了 → 再抽 20 个继续
  ⑤ 如果本次检查总耗时超过 25ms → 停一下，下次再查
```

**特点**：不是扫描所有 key（那样太慢），是随机抽样的方式。可能有些已经过期的 key 没有被抽到，暂时留在内存里。

### 惰性删除

当客户端访问一个 key 时，Redis 先检查它是否过期。如果过期了就删除，返回 null。

```bash
# 用户访问一个已经过期但还没被删除的 key
GET session:abc123       # Redis 发现它已经过期了 → 删掉 → 返回 null
```

**特点**：保证不返回已过期的数据，但过期 key 占用的内存只有在被访问时才会释放。

---

## 如果过期了但一直没被访问？

两种策略都没处理到的情况：一个 key 过期了，定期删除没抽到它，客户端也一直没访问它。

这个 key 会一直占用内存。如果这种 key 太多，**内存可能被占满**。

**解决**：Redis 配置了最大内存限制（`maxmemory`），内存不够时根据淘汰策略处理。

---

## 内存淘汰策略

当内存达到 `maxmemory` 限制时，Redis 根据配置的策略淘汰 key：

| 策略 | 行为 |
|------|------|
| `noeviction`（默认） | 不淘汰，写入直接报错 |
| `allkeys-lru` | 淘汰最近最少使用的 key（最常用） |
| `allkeys-random` | 随机淘汰 |
| `volatile-lru` | 只在设置了过期时间的 key 中淘汰最近最少使用的 |
| `volatile-ttl` | 淘汰即将过期的 key |

**项目推荐**：`allkeys-lru`——优先淘汰不常用的 key，兼顾性能和安全。

---

## vibe coding 视角

- 设置了过期时间的 key，内存不会立刻释放——不要依赖"过期了马上消失"的行为
- 大量 key 过期场景（如缓存雪崩）需要提前预防
- 看到 `EXPIRE 0` 或 `PERSIST` 时注意——这会让 key 永不过期，可能撑爆内存

## 项目关联

| 场景 | 说明 |
|------|------|
| **验证码 5 分钟过期** | `SETEX code:188xxxx 300 "123456"` — 到期自动失效 |
| **会话 Token** | `EXPIRE token:xxx 86400` — 24 小时后自动过期 |
| **限流计数器** | `INCR rate:user:1` + `EXPIRE rate:user:1 60` — 每分钟重置 |
| **内存监控** | 定期检查 Redis 内存使用量，防止过期 key 积累过多 |
