# 持久化

---

## 核心

Redis 默认数据在内存中，重启会丢失。持久化就是把内存中的数据保存到磁盘，重启后恢复。

---

## RDB——快照

**原理**：定期把内存中的所有数据生成一份全量快照，写入磁盘。

```bash
# redis.conf 配置
save 900 1         # 900 秒内至少 1 次修改 → 生成快照
save 300 10        # 300 秒内至少 10 次修改 → 生成快照
save 60 10000      # 60 秒内至少 10000 次修改 → 生成快照
```

```bash
# 手动触发
SAVE               # 同步生成，阻塞所有请求
BGSAVE             # 异步生成，不阻塞（fork 子进程处理）
```

**RDB 文件**：`dump.rdb`，二进制格式，体积小，恢复快。

| | RDB |
|--|-----|
| 数据完整性 | 可能丢数据（两次快照之间的修改） |
| 恢复速度 | 快（直接加载到内存） |
| 对性能影响 | BGSAVE fork 子进程，不影响主进程读写 |
| 文件大小 | 紧凑，比 AOF 小 |

---

## AOF——追加日志

**原理**：每执行一条写命令，追加到 AOF 文件末尾。重启时逐条重放 AOF 中的命令来恢复数据。

```bash
# redis.conf 配置
appendonly yes     # 开启 AOF
appendfsync always     # 每次写入都刷盘（最安全，最慢）
appendfsync everysec   # 每秒刷一次（折中，推荐）
appendfsync no         # 由操作系统决定（最快，最不安全）
```

**AOF 重写**：AOF 文件会越来越大，Redis 会自动压缩——把多条命令合并（如 `INCR key` 100 次合并为 `SET key 100`）。

| | AOF |
|--|-----|
| 数据完整性 | `everysec` 最多丢 1 秒数据 |
| 恢复速度 | 慢（逐条重放命令） |
| 文件大小 | 大（即使重写后也比 RDB 大） |

---

## 选哪个

| 场景 | 选哪个 | 理由 |
|------|--------|------|
| **允许丢少量数据** | RDB | 恢复快，文件小 |
| **不能丢数据** | AOF + everysec | 最多丢 1 秒数据 |
| **兼顾安全与性能** | **两者都开** | Redis 默认配置就是用 AOF + RDB |

**生产推荐**：两者都开。AOF 保证数据安全，RDB 用于快速重启恢复和备份。

---

## 为什么 Redis 快

持久化和 Redis 的快没有直接关系，这里补充 Redis 快的两个核心原因：

```
① 内存存储     → 读写速度远快于磁盘（纳秒级 vs 毫秒级）
② IO 多路复用  → 单线程处理所有请求，避免了线程切换和锁竞争
```

**IO 多路复用**简单理解：一个线程同时监视多个网络连接，哪个连接有请求就处理哪个，不需要为每个连接开一个线程。

## 项目关联

| 场景 | 说明 |
|------|------|
| **开发/测试环境** | 可以不开启持久化，重启即重置 |
| **生产环境缓存** | 可以只开 RDB，缓存丢了从数据库回源即可 |
| **生产环境数据** | 如果 Redis 存了业务数据（如 Token 黑名单），开 AOF 保证不丢 |
