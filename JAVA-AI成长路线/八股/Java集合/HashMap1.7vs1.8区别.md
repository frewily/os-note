## 总览对比表

| 特性 | JDK 1.7 | JDK 1.8 |
|------|---------|---------|
| 数据结构 | 数组 + 单向链表 | 数组 + 单向链表 + 红黑树 |
| 节点类型 | `Entry<K,V>` | `Node<K,V>`（链表）/ `TreeNode<K,V>`（树） |
| 插入方式 | 头插法 | 尾插法 |
| 哈希函数 | 4次位运算 + 5次异或（9次扰动） | 1次位运算 + 1次异或（2次扰动） |
| 扩容条件 | size >= threshold 且插入位置非空 | size > threshold |
| 扩容时机 | 先扩容再插入 | 先插入再扩容 |
| 扩容迁移 | 重新计算 hash + 头插法（链表反转） | 高位判断（原位置 or 原位置+旧容量）+ 保持顺序 |
| 并发风险 | 死循环（环形链表）+ 数据丢失 | 数据覆盖/丢失（死循环已修复） |
| 时间复杂度 | O(1) ~ O(n) | O(1) ~ O(log n) |
| 初始化 | inflateTable() 单独方法 | 集成到 resize() 中，首次 put 时懒初始化 |

## 五大核心区别详解

### 1. 数据结构：链表 → 链表+红黑树

**JDK 1.7**：只有数组 + 链表。极端情况下（大量哈希冲突），链表可能极长，get() 复杂度退化到 O(n)。

**JDK 1.8**：引入红黑树。当链表长度 > 8 且数组长度 ≥ 64 时，链表转红黑树；节点数 < 6 时退化回链表。红黑树将查找复杂度稳定在 O(log n)，即使冲突严重也能保持性能。

**6 和 8 的差值**：防止链表和树之间频繁切换（如链表长度在 8 附近波动时反复转换）。

### 2. 插入方式：头插法 → 尾插法（关键！）

**JDK 1.7 头插法**：
- 新元素插入链表头部
- 设计初衷：认为新插入的元素更可能被访问，提升缓存命中率
- **致命缺陷**：多线程并发扩容时，头插法会导致链表逆序，可能形成**环形链表**，get() 时陷入无限循环（CPU 100%）

**JDK 1.8 尾插法**：
- 新元素插入链表尾部
- 扩容时保持原有顺序，**解决了死循环问题**
- 但 HashMap **仍然不是线程安全的**（并发 put 仍可能导致数据覆盖）

### 3. 哈希函数：9次扰动 → 2次扰动

**JDK 1.7**：极其复杂的扰动（4次位运算 + 5次异或），还有 hashSeed 随机种子、String 特殊优化。目的就是死磕碰撞率。

**JDK 1.8**：简化为一行——`(h = key.hashCode()) ^ (h >>> 16)`。只做 1 次右移 + 1 次异或。
- 简化原因：引入了红黑树，即使碰撞稍多也兜得住，不需要过度扰动，换取计算速度。

### 4. 扩容迁移：重新计算 → 高位判断

**JDK 1.7**：每个元素迁移到新数组时**重新计算 hash + 取模**，然后用头插法插入（导致链表反转）。

**JDK 1.8**：利用容量是 2 的幂的特性，元素新位置只需判断：
- `(hash & oldCap) == 0` → 留在原位置
- `(hash & oldCap) != 0` → 移到 原位置 + 旧容量

不需要重算 hash，效率大幅提升。同时尾插法保持链表原有顺序。

### 5. 扩容时机：先扩容 vs 先插入

**JDK 1.7**：先扩容再插入。且条件为 `size >= threshold && 插入位置非空`——即使没满也可能触发扩容，可能造成"无效扩容"（扩容了但新元素直接放进去了）。

**JDK 1.8**：先插入再扩容。条件是 `++size > threshold`——插入后才检查。逻辑更合理，避免了无效扩容。

## 面试追问高频问题

### Q1: 为什么 JDK 1.7 头插法会死循环？

多线程同时扩容时，线程 A 和线程 B 都拿到旧链表。假设链表为 A→B→null。线程 A 迁移时用头插法逆序为 B→A，线程 B 还在用原链表。两个线程交替操作时，可能让 A.next 指向 B 且 B.next 指向 A，形成**环**。后续 get() 遍历这个环永远停不下来。

### Q2: JDK 1.8 解决了死循环，那 HashMap 线程安全了吗？

**没有。** JDK 1.8 只解决了死循环，但并发 put 仍然可能导致数据覆盖（两个线程同时读到同一个位置，各自插入，后写入的覆盖先写入的）。多线程环境仍需用 **ConcurrentHashMap**。

### Q3: 为什么链表转树阈值是 8，不是 10 或者 5？

根据**泊松分布**计算，在负载因子 0.75 下，链表长度达到 8 的概率约为 0.00000006（几乎不可能）。如果达到了，大概率是哈希函数设计有问题或被恶意攻击，此时转树是合理的止损策略。

### Q4: 为什么数组小于 64 时不转树，而是扩容？

红黑树节点占用的空间约是链表节点的 **2 倍**。数组较小时，扩容的性价比更高——扩容后元素重新分布，链表自然变短。同时避免了在小数组上维护红黑树的额外开销。
