## 模块一：Java 基础

> 中厂常问，基础分不能丢。难度较低，但答不好会直接减分。

### 1.1 面向对象三大特性是什么？各自解决什么问题？

**考察重点**：封装、继承、多态的定义 + 实际意义

**面试价值**：⭐⭐⭐（基本题，不丢分就行）

**回答骨架**：
- 封装：隐藏内部实现，对外暴露接口 → 降低耦合
- 继承：子类复用父类代码 → 避免重复
- 多态：同一行为不同实现方式 → 提高扩展性

### 1.2 == 和 equals() 的区别？

**考察重点**：比较对象引用 vs 比较内容、String 的 equals 重写

**面试价值**：⭐⭐⭐⭐（高频基础题）

**回答骨架**：
- `==` 比较的是内存地址（基本类型比值，引用类型比引用）
- `equals()` 是 Object 的方法，默认也是比地址
- String、Integer 等类重写了 equals → 比内容
- 自定义类如果要用 equals 比内容，需要自己重写

### 1.3 String、StringBuilder、StringBuffer 的区别？

**考察重点**：不可变性、线程安全、性能

**面试价值**：⭐⭐⭐

**回答骨架**：
- String 不可变（final char[]），每次修改创建新对象
- StringBuilder 可变，线程不安全，性能最好
- StringBuffer 可变，线程安全（方法加 synchronized），性能略低
- 单线程用 StringBuilder，多线程用 StringBuffer

### 1.4 接口和抽象类的区别？

**考察重点**：设计层面的区别、各自的应用场景

**面试价值**：⭐⭐⭐

**回答骨架**：
- 抽象类：is-a 关系，可以有构造方法和成员变量，单继承
- 接口：can-do 关系，JDK8 后可以有 default/static 方法，多实现
- 抽象类定义"是什么"，接口定义"能做什么"
- 能用接口优先用接口

### 1.5 异常体系结构

**考察重点**：Throwable 下的两大分支、受检/非受检异常

**面试价值**：⭐⭐

**回答骨架**：
- Throwable → Error（不可处理，如 OOM） + Exception（可处理）
- Exception → 
  - 受检异常（Checked，编译时必须处理，如 IOException、SQLException）
  - 非受检异常（RuntimeException，运行时才可能发现，如 NullPointerException）

### 1.6 泛型擦除是什么？

**考察重点**：泛型是编译期行为、运行时无泛型

**面试价值**：⭐⭐

**回答骨架**：
- 泛型信息只在编译期有效
- 编译后泛型类型被擦除为原始类型（如 `List<String>` 变 `List`）
- 运行时无法获取泛型参数的具体类型

## 模块二：Java 集合

> 🔴🔴🔴 最最最高频模块！中厂一面必问。HashMap 原理是重中之重。

### 2.1 HashMap 的 put 流程是怎样的？ 🟡 理解但不流畅（2025-05-25 首学）

**考察重点**：hash 计算 → 定位 → 插入 → 扩容 全流程

**面试价值**：⭐⭐⭐⭐⭐（几乎必考）

**回答骨架**：
1. 对 key 做 hash 计算（高 16 位异或低 16 位，减少碰撞）
2. 根据 hash 定位 bucket 位置：`(n - 1) & hash`
3. 如果 bucket 为空，直接放入新节点
4. 如果不为空，遍历链表/红黑树：
   - key 相同（hash 相等且 equals）→ 覆盖 value
   - 不同 → 追加到链表尾部（JDK8）或树节点
5. 链表长度 > 8 且数组长度 ≥ 64，转红黑树
6. 检查 size 是否 > threshold（capacity × loadFactor），是则扩容为 2 倍

### 2.2 HashMap 1.7 和 1.8 的区别？ 🟡 理解但不流畅（2026-05-26 首学）

**考察重点**：头插 vs 尾插、红黑树引入、扩容优化

**面试价值**：⭐⭐⭐⭐⭐

**回答骨架**：
- 1.7 头插法 → 1.8 尾插法（解决多线程死循环）
- 1.7 数组+链表 → 1.8 数组+链表+红黑树（>8 转树，<6 转回链表）
- 1.7 扩容时重新计算 hash → 1.8 用原位置或原位置+旧容量的方式优化

### 2.3 ConcurrentHashMap 怎么保证线程安全的？

**考察重点**：分段锁 vs CAS+synchronized

**面试价值**：⭐⭐⭐⭐⭐

**回答骨架**：
- 1.7：Segment 分段锁（继承 ReentrantLock），默认 16 个 Segment，并发度 16
- 1.8：放弃分段锁 → CAS（插入） + synchronized（链表/树头节点锁）
- 1.8 性能更好，锁粒度更细（只锁一个 bucket）

### 2.4 ArrayList 和 LinkedList 的区别？

**考察重点**：底层结构 vs 增删改查性能

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- ArrayList：数组实现，随机访问 O(1)，插入删除 O(n)
- LinkedList：双向链表，随机访问 O(n)，头尾插入删除 O(1)
- 场景：频繁随机访问 → ArrayList；频繁头尾插入删除 → LinkedList
- 注意：ArrayList 扩容是 1.5 倍

### 2.5 HashSet 怎么保证元素不重复？

**考察重点**：底层依赖 HashMap

**面试价值**：⭐⭐⭐

**回答骨架**：
- HashSet 底层是 HashMap
- add 的元素作为 HashMap 的 key，value 是一个固定常量 PRESENT
- 利用 HashMap key 不能重复的特性保证元素不重复
- 所以放入 HashSet 的元素必须重写 hashCode 和 equals

## 模块三：Java 并发

> 🔴🔴🔴 高频模块！中厂一面常问。线程池参数是必考题。

### 3.1 synchronized 的原理是什么？

**考察重点**：Java 对象头 + Monitor 锁升级过程

**面试价值**：⭐⭐⭐⭐⭐

**回答骨架**：
- synchronized 基于 Java 对象头的 Mark Word 实现
- JDK6 优化后引入锁升级过程：
  - 无锁 → 偏向锁（只有一个线程竞争） → 轻量级锁（自旋） → 重量级锁（OS 互斥量）
- 锁只能升级不能降级

### 3.2 volatile 关键字的两个作用？

**考察重点**：可见性 + 禁止指令重排序

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- **可见性**：volatile 变量的修改立即刷新到主存，其他线程读取时从主存读
- **禁止指令重排序**：volatile 读写前后插入内存屏障
- 不保证原子性（如 i++ 需要用 AtomicInteger 或 synchronized）

### 3.3 线程池的核心参数有哪些？工作流程是怎样的？

**考察重点**：7 个参数 + 4 步流程

**面试价值**：⭐⭐⭐⭐⭐（必考！）

**回答骨架**：

7 个参数：
1. corePoolSize — 核心线程数
2. maximumPoolSize — 最大线程数
3. keepAliveTime — 空闲线程存活时间
4. unit — 时间单位
5. workQueue — 任务队列（阻塞队列）
6. threadFactory — 线程工厂
7. handler — 拒绝策略

工作流程：
```
新任务提交 →
  ① 如果线程数 < corePoolSize → 创建新线程执行
  ② 如果 ≥ corePoolSize → 放入 workQueue 排队
  ③ 如果队列满 → 创建新线程直到 maximumPoolSize
  ④ 如果已达到 maximumPoolSize → 执行拒绝策略
```

### 3.4 线程池的拒绝策略有哪些？

**考察重点**：4 种内置策略

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
1. AbortPolicy（默认）：抛 RejectedExecutionException
2. CallerRunsPolicy：由提交任务的线程自己执行
3. DiscardPolicy：直接丢弃，不抛异常
4. DiscardOldestPolicy：丢弃队列中最老的任务，再尝试提交

### 3.5 ThreadLocal 的原理和内存泄漏问题？

**考察重点**：ThreadLocalMap + 弱引用 + 内存泄漏

**面试价值**：⭐⭐⭐

**回答骨架**：
- 每个 Thread 持有自己的 ThreadLocalMap
- key 是 ThreadLocal 弱引用，value 是存的值
- 内存泄漏原因：key 被回收变成 null，value 还在 → 建议用完后手动 remove()

### 3.6 lock 和 synchronized 的区别？

**考察重点**：API vs 关键字、可中断、公平锁

**面试价值**：⭐⭐⭐

**回答骨架**：
- synchronized：关键字，自动释放锁，不可中断，非公平
- Lock：接口（ReentrantLock），手动 lock/unlock，可中断，可公平
- Lock 可尝试获取锁（tryLock）、可设置等待超时
- 推荐优先用 synchronized（简单安全），需要高级功能时用 Lock

## 模块四：Spring Boot

> 🟡 中高频模块。结合项目里的拦截器、IoC 来回答，会加分。

### 4.1 IoC 和 DI 分别是什么？两者什么关系？

**考察重点**：控制反转、依赖注入的概念 + 实际好处

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- IoC（控制反转）：对象的创建权从程序员交给 Spring 容器
- DI（依赖注入）：容器自动把依赖的对象注入进来（@Autowired）
- 关系：IoC 是设计思想，DI 是它的实现方式
- 好处：降低耦合、方便测试、统一管理

### 4.2 AOP 是怎么实现的？应用场景有哪些？

**考察重点**：代理方式 + 实际场景

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 实现方式：
  - JDK 动态代理：目标类实现接口时用
  - CGLIB 代理：目标类没有接口时用（子类继承）
- 应用场景：日志、事务、权限校验、耗时统计
- 本项目里：拦截器算 AOP 思想的体现（横切关注点分离）

### 4.3 Bean 的生命周期？

**考察重点**：从创建到销毁的完整流程

**面试价值**：⭐⭐⭐

**回答骨架**：
1. 实例化（new）
2. 属性赋值（依赖注入）
3. 初始化前（@PostConstruct 或 InitializingBean）
4. 初始化（afterPropertiesSet / init-method）
5. 初始化后（AOP 代理在此生成）
6. 使用 Bean
7. 销毁（@PreDestroy / DisposableBean）

### 4.4 拦截器（Interceptor）和过滤器（Filter）的区别？

**考察重点**：作用范围、执行顺序、控制粒度

**面试价值**：⭐⭐⭐⭐（结合项目讲加分）

**回答骨架**：
- Filter：Servlet 规范，对所有请求有效，在拦截器之前执行
- Interceptor：Spring 提供，只对 Controller 请求有效，可以拿到 Handler 和方法
- 本项目里：JwtAuthInterceptor、RateLimitInterceptor、ProcessTimeInterceptor 层层拦截
- 拦截器可以多次调用（preHandle → postHandle → afterCompletion），Filter 只有一次

### 4.5 @Autowired 和 @Resource 的区别？

**考察重点**：注入方式（byType vs byName）

**面试价值**：⭐⭐⭐

**回答骨架**：
- @Autowired：Spring 的，按类型注入（byType），配合 @Qualifier 可指定名称
- @Resource：Java 的，默认按名称注入（byName），找不到再按类型
- 如果有多个同类型的 Bean，@Autowired 会报错，需要用 @Qualifier

### 4.6 Spring Boot 自动配置的原理？

**考察重点**：@EnableAutoConfiguration → spring.factories → 条件注解

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
1. `@SpringBootApplication` 包含 `@EnableAutoConfiguration`
2. 扫描 `META-INF/spring.factories` 文件中的配置类
3. 配合 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 等条件注解
4. 条件满足才自动配置（如 Classpath 下有 DataSource 才配数据源）

## 模块五：MySQL

> 🔴🔴🔴 高频模块！中厂一面必问。B+Tree 和事务隔离级别是重中之重。

### 5.1 为什么 MySQL 用 B+Tree 做索引结构？

**考察重点**：B+Tree 的特点 vs 其他结构对比

**面试价值**：⭐⭐⭐⭐⭐

**回答骨架**：
- B+Tree 所有数据在叶子节点，非叶子节点只存 key → 非叶子节点能存更多 key → 树更矮
- 叶子节点用双向链表连接 → 范围查询直接走链表，不需要回到父节点
- 对比二叉树：树太高，IO 次数多
- 对比 B-Tree：B-Tree 非叶子节点也有数据，能存的 key 更少，树更高
- 对比哈希索引：不支持范围查询

### 5.2 聚簇索引和非聚簇索引的区别？

**考察重点**：数据和索引是否在一起、回表

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 聚簇索引（InnoDB）：索引和数据在一起，叶子节点存整行数据
  - 主键索引就是聚簇索引
  - 一个表只能有一个聚簇索引
- 非聚簇索引（二级索引）：叶子节点存主键值
  - 通过非聚簇索引查询需要先找到主键 → 再回表查完整数据
  - 覆盖索引不需要回表

### 5.3 最左前缀法则是什么？

**考察重点**：联合索引的匹配规则

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 联合索引 (a, b, c)，查询条件必须从最左列开始匹配
- 跳过了某一列，后面的列无法使用索引
- 如 (a, b, c) 索引：`where a=1 and b=2` 可以用；`where b=2` 不可以用
- MySQL 8.0 后即使跳过中间列，部分场景也能用索引下推

### 5.4 事务的四大特性（ACID）是什么？

**考察重点**：每个特性解决什么问题

**面试价值**：⭐⭐⭐

**回答骨架**：
- 原子性（A）：事务要么全部成功，要么全部回滚 → undo log 实现
- 一致性（C）：事务前后数据状态一致 → AID 共同保证
- 隔离性（I）：并发事务互不干扰 → 锁 + MVCC 实现
- 持久性（D）：事务提交后数据永久保存 → redo log 实现

### 5.5 事务隔离级别有哪些？分别解决什么问题？

**考察重点**：4 个级别 + 3 种并发问题

**面试价值**：⭐⭐⭐⭐⭐（必考！）

**回答骨架**：

3 种并发问题：
1. 脏读：读到另一个事务未提交的数据
2. 不可重复读：同一事务内两次读同一行，结果不同
3. 幻读：同一事务内两次范围查询，结果行数不同

4 个隔离级别：
| 级别 | 解决 |
|------|------|
| 读未提交 | 什么都不解决 |
| 读已提交（RC） | 解决脏读 |
| 可重复读（RR，MySQL 默认）| 解决脏读 + 不可重复读 |
| 串行化 | 解决脏读 + 不可重复读 + 幻读 |

InnoDB 在 RR 级别通过间隙锁解决幻读

### 5.6 MVCC 的原理是什么？

**考察重点**：隐藏字段 + undo log + ReadView

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 每行数据有隐藏字段：DB_TRX_ID（事务ID），DB_ROLL_PTR（回滚指针）
- undo log 记录数据的历史版本 → 形成版本链
- ReadView 决定当前事务能"看到"哪个版本
  - RC 级别：每次查询生成新的 ReadView
  - RR 级别：第一次查询生成 ReadView，之后复用
- 实现了"读不加锁"

### 5.7 说说 MySQL 的锁机制

**考察重点**：行锁、表锁、间隙锁、临键锁

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 行锁（Record Lock）：锁住索引记录
- 间隙锁（Gap Lock）：锁住两个索引值之间的间隙，防止幻读
- 临键锁（Next-Key Lock）：行锁 + 间隙锁，InnoDB RR 级别默认用
- 表锁：锁住整张表
- 意向锁：表级别的标志，告诉其他事务"有人要锁行"

## 模块六：Redis

> 🔴 高频模块。数据结构 + 缓存场景是中厂最爱问的。

### 6.1 Redis 的五种基本数据类型及应用场景？

**考察重点**：类型名 + 底层结构 + 典型场景

**面试价值**：⭐⭐⭐⭐⭐

**回答骨架**：
| 类型 | 底层实现 | 典型场景 |
|------|---------|---------|
| String | SDS（动态字符串）| 缓存、计数器、分布式锁 |
| Hash | ziplist / dict | 对象存储 |
| List | quicklist | 消息队列、最新列表 |
| Set | intset / dict | 去重、共同好友 |
| Sorted Set (ZSet) | ziplist / skiplist+dict | 排行榜、延时队列 |

### 6.2 缓存穿透、缓存击穿、缓存雪崩的区别和解决方案？

**考察重点**：三种现象 + 各自解法

**面试价值**：⭐⭐⭐⭐⭐（必考！）

**回答骨架**：
- **缓存穿透**：查询一个不存在的数据，缓存和数据库都没有
  - 方案：布隆过滤器 / 缓存空值（短期）
- **缓存击穿**：一个热点 key 过期，大量请求打到数据库
  - 方案：互斥锁（setnx）/ 热点 key 永不过期
- **缓存雪崩**：大量 key 同时过期 / Redis 宕机
  - 方案：过期时间加随机值 / 集群部署 / 熔断降级

### 6.3 Redis 的过期删除策略

**考察重点**：定期删除 + 惰性删除

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- 定期删除：每隔 100ms 随机抽取部分 key 检查并删除过期 key
- 惰性删除：访问 key 时才检查是否过期，过期则删除
- 两种配合使用，不是定时扫描所有 key

### 6.4 Redis 持久化方式：RDB 和 AOF 的区别？

**考察重点**：快照 vs 日志、数据完整性、性能

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
| | RDB | AOF |
|---|-----|-----|
| 方式 | 定期生成数据快照 | 追加写操作日志 |
| 文件大小 | 小 | 大（可重写压缩）|
| 数据完整性 | 可能丢数据（两次快照之间） | 根据 fsync 策略可以做到不丢 |
| 恢复速度 | 快 | 慢 |
| 是否阻塞 | save 阻塞，bgsave 不阻塞 | 不阻塞 |

## 模块七：计算机网络

> 🟡 中厂有时会问，尤其是 TCP 和 HTTP 相关。不是最核心模块，但面试问到答不上来会减分。

### 7.1 TCP 三次握手和四次挥手

**考察重点**：每次握手/挥手的含义、状态变化

**面试价值**：⭐⭐⭐⭐

**回答骨架**：

**三次握手**：
1. 客户端发 SYN → 服务端（告诉服务端"我要连接"）
2. 服务端回 SYN+ACK → 客户端（告诉客户端"收到了，我准备好了"）
3. 客户端发 ACK → 服务端（告诉服务端"我也准备好了"）
→ 连接建立

**四次挥手**：
1. 客户端发 FIN → 服务端（告诉服务端"我要关闭"）
2. 服务端回 ACK → 客户端（告诉客户端"收到你的关闭请求"）
3. 服务端发 FIN → 客户端（告诉客户端"我也要关闭了"）
4. 客户端回 ACK → 服务端（告诉服务端"收到"）
→ 连接关闭

### 7.2 HTTP 和 HTTPS 的区别？

**考察重点**：SSL/TLS、端口、证书

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- HTTP：明文传输，端口 80
- HTTPS：HTTP + SSL/TLS 加密传输，端口 443
- HTTPS 需要 CA 证书验证身份
- HTTPS 握手机制：非对称加密交换对称密钥 → 后续用对称加密通信

### 7.3 GET 和 POST 的区别？

**考察重点**：语义区别、幂等性、请求体

**面试价值**：⭐⭐⭐

**回答骨架**：
- GET：获取资源，参数在 URL，长度有限制，幂等（多次请求结果相同）
- POST：提交/处理数据，参数在请求体，不幂等
- GET 请求会被浏览器缓存，POST 不会
- 安全性：都不安全（HTTPS 才安全），GET 参数在 URL 中更容易暴露

### 7.4 Cookie 和 Session 的区别？

**考察重点**：存储位置、跨域、结合 JWT 对比

**面试价值**：⭐⭐⭐

**回答骨架**：
- Cookie：客户端存储（浏览器），每次请求自动携带
- Session：服务端存储，依赖 Cookie（sessionId 存在 Cookie 中）
- 本项目用 JWT 代替了 Session，因为：
  - 无状态：不需要在服务端存 session
  - 跨域友好：前后端分离场景下 Session 不好用

## 模块八：项目相关八股

> 🟡🟡🟡 这部分面试官会根据你的项目来问。结合 Agent 项目来答，展示自己的项目理解深度。

### 8.1 为什么用 JWT 不用 Session？

**考察重点**：无状态 vs 有状态、分布式场景

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- Session：服务端存储 session 信息 → 分布式下需要共享存储（如 Redis）
- JWT：token 本身携带用户信息 → 服务端不需要存 → 天然支持分布式
- JWT 缺点：无法主动失效（过期前一直有效）、payload 不能放敏感信息（只 base64 编码）
- 本项目用 JWT + 拦截器实现认证

### 8.2 SSE 和 WebSocket 的区别？为什么选 SSE？

**考察重点**：通信方向、协议、场景选型

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
| | SSE | WebSocket |
|---|-----|----------|
| 通信方向 | 服务端→客户端（单向） | 双向通信 |
| 协议 | 基于 HTTP | 独立协议（ws://）|
| 兼容性 | 浏览器原生支持 | 更高，但复杂些 |
| 自动重连 | 内置（EventSource）| 需要自己实现 |
| 适用场景 | LLM 流式输出、通知推送 | 聊天室、协同编辑、游戏 |

- 本项目选 SSE 的原因：LLM 输出是服务端单向推送 → 不需要双向 → SSE 更轻量

### 8.3 流式输出（Streaming）的实现原理？

**考察重点**：从 LangChain Streaming → FastAPI → WebClient → SSE 整条链路

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
1. LangChain 侧：`ChatOpenAI(streaming=True)` → Generator 逐 chunk yield
2. FastAPI 侧：`StreamingResponse` 将 Generator 转为 SSE 格式：`data: ...\n\n`
3. Spring Boot 侧：`WebClient` 非阻塞接收 Flux → 透传给前端
4. 前端侧：`EventSource` 或 `fetch` 逐块解析 → 追加到页面

### 8.4 RAG 的完整链路是什么？

**考察重点**：检索 → 重排序 → 增强 → 生成 四个步骤

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
1. **检索**：用户提问 → Embedding 向量化 → ChromaDB 余弦相似度检索 TopK
2. **重排序**：CrossEncoder 对 TopK 结果重新打分排序 → 提高精度
3. **增强**：把检索结果注入 Prompt（"根据以下文档回答问题"）
4. **生成**：LLM 基于增强后的 Prompt 生成带引用的回答

### 8.5 ReAct Agent 是怎么工作的？

**考察重点**：Thought → Action → Observation 循环

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
- ReAct = Reasoning + Acting
- 循环过程：
  1. Thought（思考）：LLM 判断当前是否需要调用工具
  2. Action（行动）：如果需要，输出工具调用指令（工具名 + 参数）
  3. Observation（观察）：工具执行结果返回给 LLM
  4. 回到 Thought → 直到 LLM 认为不需要调工具了 → 输出最终回答
- 本项目里：Agent 收到问题 → 判断是否要检索文档 → 调用 rag_search 工具 → 基于检索结果回答

### 8.6 这个项目为什么用混合架构（Java + Python）？

**考察重点**：技术选型的决策能力

**面试价值**：⭐⭐⭐⭐⭐（差异化亮点问题！）

**回答骨架**：
- LangChain 是 Python 生态，Java 没有成熟等价库
- 方案对比：
  - 全 Python：业务层能力弱（认证/限流/持久化不如 Spring Boot 成熟）
  - 全 Java：没有成熟的 Agent/RAG 框架
  - 混合架构：各司其职 → Spring Boot 做 Web 业务 / Python 做 AI 推理
- 通信：HTTP + JSON，简单可靠
- 代价：增加了一次网络开销，但对比 LLM 本身的推理耗时可以忽略

### 8.7 项目里 Redis 的双重角色是什么？

**考察重点**：Cache-Aside 缓存 + 限流

**面试价值**：⭐⭐⭐⭐

**回答骨架**：
1. **缓存**：Cache-Aside 模式 → 先读 Redis，没有则查 MySQL 再回写 Redis
2. **限流**：Redis INCR + 过期时间实现滑动窗口限流
   - 每个用户每分钟限制 N 次请求
   - INCR 原子递增，第一次设置过期时间
   - 超过阈值返回 429
