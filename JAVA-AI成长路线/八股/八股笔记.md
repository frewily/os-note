## 模块二：Java 集合

### 2.1 HashMap put 流程（🟡 2026-05-25）

> 面试价值：⭐⭐⭐⭐⭐

#### 整体结构

HashMap 底层 = **数组 + 链表 + 红黑树**（JDK 8）。数组每个位置叫 bucket，存链表或红黑树的头节点。

#### put 完整 6 步

```
① 扰动 hash：key.hashCode() ^ (h >>> 16)      → 高位参与低位计算，减少碰撞
② 定位：index = (n - 1) & hash                → 位运算替代取模（n 需为 2 的幂次）
③ bucket 为空 → 直接插入新节点
④ bucket 非空 → 遍历链表/红黑树：
     ├ key 相同（hash 相等 && equals 相等）→ 覆盖 value
     └ key 不同 → JDK8 尾插法追加到链表末尾
⑤ 链表 > 8 且数组 ≥ 64 → 链表转红黑树（O(n)→O(log n)）；< 6 退回链表
⑥ size > threshold（16 × 0.75 = 12）→ 数组翻倍扩容
```

#### 扰动函数

```java
hash = key.hashCode() ^ (key.hashCode() >>> 16)
```

- `>>> 16`：高 16 位移到低 16 位，高位补 0
- `^` 异或：相同 0，不同 1
- 作用：当 n=16 时 `(n-1)&hash` 只用低 4 位，高位浪费。扰动后高位混入低位，减少碰撞

#### 为什么数组长度必须是 2 的幂次

1. **位运算代替取模**：`(n-1) & hash` 等价于 `hash % n`，但 `&` 比 `%` 快一个数量级。n=2^k 时 n-1 二进制全 1
2. **扩容优化**：JDK8 扩容时新位置 = 原位置 or 原位置 + 旧容量，看 hash 新增 bit 位是 0 还是 1，不用重算

#### 红黑树阈值

| 条件         | 阈值  | 说明               |
| ---------- | --- | ---------------- |
| 链表→红黑树     | > 8 | 同时要求数组 ≥ 64      |
| 红黑树→链表     | < 6 | 6-8 差值防频繁切换      |
| 链表>8但数组<64 | 先扩容 | 扩容后元素重新分布，链表自然变短 |

#### 扩容

- **触发**：`size > capacity × loadFactor`（默认 16 × 0.75 = 12）
- **方式**：数组翻倍（16→32→64...）
- **负载因子 0.75**：空间与时间折中，泊松分布统计学结果

#### JDK 7 vs JDK 8 差异速览

| <br />  | JDK 7        | JDK 8          |
| ------- | ------------ | -------------- |
| 数据结构    | 数组+链表        | 数组+链表+红黑树      |
| 插入方式    | 头插法（并发可能死循环） | 尾插法            |
| 扩容 hash | 重新计算         | 原位置 or 原位置+旧容量 |
| 扩容时机    | 先扩容再插入       | 先插入再扩容         |

#### 与项目关联

- HashSet 底层就是 HashMap（value 占位常量 PRESENT）
- 黑马点评高并发场景需用 ConcurrentHashMap 替代

#### 面试应对

- 口述 6 步 → 基础分
- 说"扰动函数让高位参与索引" → 加分
- 说"扩容新位置=原位置 or 原位置+旧容量" → 看过源码
- 关键数字：16、0.75、8、64、6、2 倍

#### 常见疑问

**Q1：为什么 key 相等要求 hash 相等 && equals 相等，一个条件不够吗？**

A：因为 hash 相同不代表 key 一定相同（哈希冲突本身存在）。只用 equals 可以但性能差——先比 int 型的 hash 做快速过滤，hash 相同再用 equals 精准确认。这是典型的"先粗筛后精排"（跟RAG 链路里的两阶段检索思维一样——向量检索粗筛 + CrossEncoder 精排）。

**Q2：转红黑树后新元素还插链表末尾吗？**

A：不是。链表和红黑树互斥存在，一个 bucket 同一时刻只有一种结构。链表用尾插，红黑树用红黑树的插入规则。TreeNode 内部虽维护双向链表供转换用，但那是实现细节。

### 2.2 HashMap 1.7 vs 1.8 区别（🟡 2026-05-26）

> 面试价值：⭐⭐⭐⭐⭐

#### 五维对比

| 维度       | JDK 1.7                             | JDK 1.8                            |
| -------- | ----------------------------------- | ---------------------------------- |
| **数据结构** | 数组 + 链表                             | 数组 + 链表 + 红黑树                      |
| **插入方式** | 头插法                                 | 尾插法                                |
| **扩容迁移** | 重新计算 hash + 头插（链表反转）                | 仅判断 `hash & oldCap`：0 留原位，1→原位+旧容量 |
| **扩容时机** | 先扩容再插入 + 条件（size≥threshold 且插入位置非空） | 先插入再扩容 + 无条件（size > threshold）     |
| **哈希函数** | 9 次扰动（4 移位+5 异或）                    | 2 次扰动（`h ^ (h>>>16)`）              |

#### 各维度详解

**1. 数据结构**

- 1.7 只有链表，冲突严重时 get 退化为 O(n)
- 1.8 引入红黑树，最坏情况 O(log n)。链表 > 8 且数组 ≥ 64 转树，< 6 退链表

**2. 头插法为什么死循环**

- 头插法每次把新元素插到链表最前面
- 扩容时遍历旧链表，用头插法迁移到新数组 → 链表必然反转
- 多线程同时扩容：线程 A 逆序后的链表与线程 B 还没逆序的链表交叉引用 → 形成环 → get() 死循环
- 1.8 尾插法顺序不变，环就不可能形成

**3. 扩容优化**

- 1.7 每个元素重新算 hash + 取模，效率低
- 1.8 利用 2 倍扩容特性，只看 hash 在"新增 bit 位"上是 0 还是 1，不用重算

**4. 扩容时机**

- 1.7：先检查要不要扩，再插新元素。条件：`size >= threshold && 插入位置非空`
- 1.8：先插进去，再检查 `size > threshold`。逻辑更统一

**5. 哈希函数**

- 1.7：拼命减少碰撞（9 次扰动），因为没有红黑树兜底
- 1.8：简化扰动（2 次），因为红黑树兜底了——空间换时间

#### ⚠️ 注意

1.8 只修了死循环，HashMap **仍然不是线程安全的**（并发 put 还会数据覆盖）。多线程环境必须用 ConcurrentHashMap。

### 2.3 ConcurrentHashMap 线程安全原理（🟡 2026-05-27）

> 面试价值：⭐⭐⭐⭐⭐

#### 为什么需要它

| 实现 | 问题 |
|------|------|
| HashMap | 线程不安全（数据覆盖/死循环） |
| Hashtable | 全表 synchronized，性能极低 |
| ConcurrentHashMap | 锁粒度细化，高并发首选 |

#### 1.7：Segment 分段锁

- 数据分成 16 个 Segment（默认），每个 Segment 继承 **ReentrantLock**，是一把独立锁
- 写操作只锁一个 Segment，不同 Segment 间完全并行
- 并发度 = Segment 数量（默认 16）

#### 1.8：CAS + synchronized

- 抛弃 Segment，结构和 HashMap 一样（**Node 数组 + 链表 + 红黑树**）
- 锁粒度细化到**每个桶**的头节点

**三种情况：**
| 场景 | 策略 | 原因 |
|------|------|------|
| 桶为空 | CAS 无锁插入 | 预期值为 null，竞争少 |
| 桶非空 | synchronized 锁头节点 | 只锁这一个桶，其他桶不受影响 |
| 扩容中 | 多线程协助扩容 | helpTransfer 分担压力 |

#### 为什么 get 不用加锁

Node 的 `val` 和 `next` 用 **volatile** 修饰，保证可见性。一个线程修改后，其他线程立刻能读到最新值。

#### 1.7 vs 1.8 对比

| 维度 | 1.7 | 1.8 |
|------|-----|-----|
| 结构 | Segment + HashEntry 链表 | Node 数组 + 链表 + 红黑树 |
| 锁机制 | ReentrantLock（分段锁） | CAS（空桶）+ synchronized（非空桶） |
| 锁粒度 | 一个 Segment（含多个桶） | 一个桶的头节点 |
| 并发度 | 默认 16 | 理论等于数组长度 |
| get | 无锁 volatile | 无锁 volatile |

#### 常见疑问

**Q1：volatile 是什么？为什么 get 不用加锁？**

A：CPU 每个核心有自己的高速缓存。普通变量修改后可能还留在缓存里没写回主存，其他线程读不到最新值。volatile 强制每次读写都直接操作主存，不经过缓存。所以 ConcurrentHashMap 的 Node.val 和 Node.next 用 volatile 修饰后，写线程改了值立刻可见，读线程无需加锁就能拿到最新值。

**Q2：CAS 是什么？**

A：CAS（Compare And Swap）是把"检查条件 + 执行操作"打包成一个不可拆分的原子操作。比如"检查桶是否为空，如果为空就插入"——这两步打包后不会被其他线程打断，避免了先检查再写入之间被覆盖的问题。效果是**无锁并发**：不需要加重量级锁就能安全完成操作。

**Q3：桶（bucket）指的是什么？**

A：HashMap/ConcurrentHashMap 底层是一个数组，数组的每个位置就是一个桶（bucket），存的是链表头节点或红黑树根节点。

**Q4：CAS 打包有什么效果？**

A：防止多线程数据覆盖。两个线程同时发现桶为空，如果不打包，A 检查完空→B 也检查完空→B 先写入→A 再写入就把 B 的覆盖了。CAS 打包后，A 写入时会再次确认"还是空吗？"——如果已被 B 占了，就不写了，改为加锁处理。
