## D1 面向对象、接口与抽象类、异常体系

### D1-1 面向对象三大特性？各自解决什么问题？（🟡 理解但不流畅）

**考察重点**：封装/继承/多态定义 + 实际意义，而不是背名词

**项目联系**：DTO/VO/Service 分层、Controller 只收参返回

**回答骨架**：
- **封装**：**隐藏内部实现，对外暴露方法接口** → **降低耦合**、保护数据不被乱改
  - 项目：Service 封装业务细节，Controller 只负责收参/返回；DTO/VO 隔离内部实体，不让数据库实体直接暴露给前端
- **继承**：子类**复用**父类代码并可扩展 → 消除重复  **is-a关系**
- **多态**：同一行为，不同子类有不同实现（父类引用指向子类对象），编译看左边，运行看右边
  - 三条件：继承/实现 + 方法重写 + 父类引用指向子类对象
  - 项目：面向接口编程（Service 接口 + 多实现），策略模式

**本轮复述记录**：
- 已掌握：封装是隐藏细节、暴露接口，可降低耦合并保护数据；多态是“编译看左边、运行看右边”，同一接口可以有不同实现。
- 待加强：继承不只是代码复用，还要强调 `is-a` 类型关系；继承会增加父子类耦合，不宜简单说成必然“破坏封装”。多态要补充“继承/实现、重写、父类引用指向子类对象”三个条件，以及新增实现时调用方无需修改。

### D1-2 接口和抽象类的区别？怎么选？（🟡 理解但不流畅）

**考察重点**：设计层面区别（is-a vs can-do）、JDK8+ 接口变化

**项目联系**：Service 接口 + Impl 为什么这么拆

**回答骨架**：
- **继承关系**：抽象类只能单继承；类可以实现多个接口；接口可以继承多个接口。
- **抽象类**：表达 `is-a` 关系，可以有构造方法、实例成员变量、抽象方法和普通方法，用于复用状态和共性实现。
- **接口**：表达 `can-do` 能力和规范，不能有构造方法和实例字段；字段默认是 `public static final` 常量，Java 8+ 可定义 `default`/`static` 方法。
- **项目联系**：`Service` 接口定义业务能力和规范，`ServiceImpl` 提供实现；Controller 依赖接口，便于替换实现和测试。

**本轮复述记录**：
- 已掌握：抽象类单继承，接口可继承多个接口；接口表达 `can-do` 能力和规范，抽象类表达 `is-a` 关系并抽取共性；Service 常用接口定义规范、Impl 提供具体实现。
- 待加强：抽象类是“可以有”构造方法、成员变量和普通方法，不是“实现构造方法”；接口不能有实例字段和构造方法，字段默认是 `public static final` 常量，Java 8+ 可以有 `default`/`static` 方法。


### D1-3 Java 异常体系？项目里怎么处理异常？（🟡 理解但不流畅）

**考察重点**：Throwable 两大分支、受检/非受检、Spring 事务回滚规则

**项目联系**：全局异常处理器、业务异常设计

**回答骨架**：
- `Throwable` → `Error` + `Exception`。
- `Error`：JVM/系统层面的严重错误，通常无法恢复，例如 OOM、StackOverflow；它不是受检异常。
- `Exception`：程序运行中可能处理的异常；其中 `RuntimeException` 是非受检异常，其他常见 `Exception` 是受检异常。
- **受检异常**：编译器强制处理，可以 `try-catch` 或 `throws`，如 IOException。
- **非受检异常**：编译器不强制处理，常见于参数非法、空指针等，如 IllegalArgumentException、NullPointerException。
- 项目：参数校验失败或 Python 服务调用失败时抛出 `BizException extends RuntimeException`，由 `@RestControllerAdvice` + `@ExceptionHandler` 统一转换为错误响应；底层异常按需记录日志并包装，避免直接暴露内部细节。

**本轮复述记录**：
- 已掌握：Throwable 分为 Error 和 Exception；知道受检/非受检异常，以及 try-catch、throws 和 Spring 全局异常处理。
- 易错点：Error 不是外部错误，也不是受检异常；受检异常是编译器强制要求处理的异常，非受检异常通常是 RuntimeException，编译器不强制处理。

## D2 String、包装类、泛型、反射与注解

### D2-1 String、StringBuilder、StringBuffer 的区别？（🟡 理解但不流畅）

**考察重点**：可变性、线程安全、性能和使用场景

**回答骨架**：
- **String**：不可变，适合内容基本不变或少量拼接的场景；**不可变对象可以安全共享，字符串字面量还可以使用字符串常量池。**
- **StringBuilder**：可变，线程不安全，适合单线程下频繁拼接，通常性能更好。
- **StringBuffer**：可变，方法大量使用 `synchronized`，线程安全，但有额外同步开销，通常比 `StringBuilder` 慢。
- 注意：简单的 `+` 拼接可能被编译器优化；循环中频繁拼接通常使用 `StringBuilder`。

**本轮复述记录**：
- 已掌握：String 不可变；StringBuilder 和 StringBuffer 可变；StringBuilder 适合单线程频繁修改；StringBuffer 线程安全但性能有额外开销。
- 待加强：String 的不可变性为什么有利于安全共享，以及字符串常量池；不要绝对化地说 String 性能一定最低，要结合拼接次数和编译器优化判断。

### D2-2 `==` 和 `equals()` 有什么区别？（🟡 理解但不流畅）

**回答骨架**：
- 基本类型使用 `==` 比较值；引用类型使用 `==` 比较两个引用**是否指向同一个对象**。
- `equals()` 是 `Object` 的方法，默认效果与引用类型的 `==` 类似，比较对象身份。
- `String`、包装类等通常**重写**了 `equals()`，按照**对象内容**进行比较。
- 自定义类如果希望按内容判断相等，需要重写 `equals()`，并遵守相等对象必须有相同 `hashCode` 的约定。(所以一个类重写了 equals()，通常还必须重写 hashCode()）

**本轮复述记录**：
- 已掌握：`==` 比较基本类型的值或引用类型的对象身份；`Object.equals()` 默认比较身份；String 重写后按内容比较。
- 表述优化：引用类型的 `==` 更严谨地说是比较引用是否指向同一个对象，不直接表述为比较内存地址。
- 追问已掌握：**HashMap/HashSet 先根据 `hashCode()` 定位**，再使用 `equals()` 判断；相等对象必须有相同 `hashCode()`，否则可能查询失败或出现重复元素。

### D2-3 什么是包装类？为什么需要包装类？（🟢 基本掌握）

**回答骨架**：
- 包装类是基本类型对应的对象类型，例如 `int` 对应 `Integer`、`char` 对应 `Character`。
- 需要包装类的原因：集合和泛型只能使用对象；包装类提供工具方法；包装类可以表示 `null`，基本类型不能。
- **自动装箱**：基本类型自动转换为对应包装类，如 `Integer n = 10`。
- **自动拆箱**：包装类自动转换为对应基本类型，如 `int n = integer`。
- 注意：包装类为 `null` 时自动拆箱会抛出 `NullPointerException`。
- 总结：包装类是基本数据类型对应的对象类型。它主要用于集合和泛型、提供工具方法，并且可以表示 null。自动装箱是基本类型转包装类，自动拆箱是包装类转基本类型。

**本轮复述记录**：
- 已掌握：包装类是基本类型对应的对象类型；知道集合/泛型、工具方法、`null` 是使用包装类的主要原因；理解自动装箱和拆箱。
- 追问已掌握：`Integer.valueOf()` 通常缓存 `-128` 到 `127` 的整数；缓存范围内可能复用同一对象，`==` 可能为 `true`，范围外通常是不同对象；包装类数值比较应使用 `equals()`。

### D2-4 什么是 Java 泛型？什么是泛型擦除？（🟢 基本掌握）

**回答骨架**：
- 泛型是编译期的类型参数机制，用于限制集合或类/方法允许使用的类型。
- 作用：编译期发现类型错误；取值时自动完成类型转换，减少强制类型转换。
- 泛型擦除：Java 泛型主要在编译期生效，编译成字节码后，运行时通常不保留具体泛型参数；`List<String>` 和 `List<Integer>` 运行时通常都是 `List`。（泛型是java5后面才有的，为了向后兼容，运行时不带上泛型）
- 常见限制：不能直接 `new T()`，不能直接判断 `instanceof List<String>`。

**本轮复述记录**：
- 已掌握：泛型可以限制集合类型、提前发现类型错误、减少取值时的强制转换；知道泛型参数在编译为字节码后通常会被擦除。

### D2-5 什么是 Java 反射？有什么应用？（🟢 基本掌握）

**回答骨架**：
- 反射是程序运行时动态获取类的信息，并创建对象、访问成员变量、调用方法的机制。
- 可以获取类名、父类、接口、构造方法、字段、方法和注解等信息。
- 常见应用：Spring 根据注解创建 Bean 和依赖注入；Spring MVC 根据映射注解分发请求；MyBatis 完成实体与数据库字段映射；JUnit 查找测试方法。
- 缺点：性能和可读性较差，绕过部分编译期检查，访问私有成员还可能带来安全问题。

**本轮复述记录**：
- 已掌握：反射是在运行时动态获取类信息，并动态创建对象、访问属性和调用方法；Spring 等框架大量使用反射。

### D2-6 什么是 Java 注解？有什么作用？（🟡 理解但不流畅）

**回答骨架**：
- 注解是一种给类、方法、字段等代码元素添加的元数据，格式通常是 `@AnnotationName`。
- 编译器、开发工具或框架可以读取注解，并据此执行检查、生成代码或完成运行时处理。
- Spring 常见注解：`@Controller`、`@Service`、`@Autowired`、`@RequestMapping`；MyBatis 常见 `@Mapper`。
- `@Service` 本身不是创建对象的代码；Spring 启动时扫描到带有该注解的类，再通过反射等机制注册 Bean、管理其生命周期，之后才能完成依赖注入。
- 保留策略：`SOURCE` 只保留在源码；`CLASS` 保留到字节码；`RUNTIME` 运行时仍可通过反射读取。

**本轮复述记录**：
- 已掌握：注解是给类、方法、字段等代码元素添加的元数据，编译器、工具或框架可以据此执行处理。
- 已补充：`@Service` 让 Spring 扫描到该类后，将其注册成 Spring Bean，再由容器管理并支持依赖注入。
- 已掌握：注解保留策略 `SOURCE`、`CLASS`、`RUNTIME` 的区别；`@Service` 使用运行时保留策略，Spring 通过扫描和反射注册 Bean。

### D3-1 `ArrayList` 和 `LinkedList` 的区别？（🟡 理解但不流畅）

**回答骨架**：
- `ArrayList` 底层是动态数组，`LinkedList` 底层是双向链表。
- `ArrayList` 按下标随机访问通常是 `O(1)`；`LinkedList` 按下标访问通常是 `O(n)`，需要定位节点。
- `ArrayList` 中间插入/删除通常是 `O(n)`，因为要移动元素；`LinkedList` 已知节点位置时插入/删除是 `O(1)`，但定位节点仍可能是 `O(n)`。
- 两者都能保持插入顺序；实际开发通常优先 `ArrayList`，频繁头尾操作可考虑 `ArrayDeque`。
- 实际性能还受连续内存带来的 CPU 缓存友好性影响，`LinkedList` 节点还会有额外指针内存开销。

**本轮复述记录**：
- 已掌握：底层结构、随机访问差异，以及 LinkedList 插入删除前需要先定位节点。
- 待加强：不要简单说“顺序存储用 LinkedList”；插入删除复杂度要区分“已知节点”和“需要先查找”。

### D3-2 `ArrayList` 的扩容机制？（🟡 理解但不流畅）

**回答骨架**：
- 当元素数量达到当前容量时触发扩容。
- 常见 JDK 实现中，新容量约为旧容量的 `1.5` 倍，计算类似 `oldCapacity + (oldCapacity >> 1)`。
- 创建更大的新数组，并使用数组复制把旧元素迁移过去。
- JDK 8 默认构造的 `ArrayList` 初始可能使用空数组，第一次添加元素时才分配默认容量。
- 扩容会带来复制成本，因此可以根据数据量预估容量，使用 `new ArrayList<>(expectedSize)` 减少扩容。

**本轮复述记录**：
- 已掌握：容量达到上限时扩容，扩容到原来的约 1.5 倍，并复制原数组元素。
- 待加强：默认构造的懒分配细节，以及扩容会产生数组复制成本。

### D3-3 `HashMap.put(key, value)` 的流程？（🟡 理解但不流畅）

**回答骨架**：
- 对 key 的 `hashCode()` 做扰动计算，再通过 `(n - 1) & hash` 定位桶下标。
- 桶为空：直接创建节点放入。
- 桶不为空：比较 hash 和 key 的 `equals()`；相同则覆盖 value，不同则继续查找链表或红黑树。
- 链表中找不到相同 key 时，新增节点；冲突严重时，链表达到 8 且数组容量至少 64，转为红黑树。
- 插入后如果 `size > threshold`，触发扩容；默认负载因子为 `0.75`，容量通常扩为原来的 2 倍。

**本轮复述记录**：
- 已掌握：hash 定位、空桶插入、相同 key 覆盖、冲突时查找链表/红黑树、树化条件和负载因子。
- 待加强：扰动 hash、`hash + equals` 的判断、红黑树不是尾插，以及扩容判断比较的是 `size` 和 `threshold`。
- 追问已掌握：数组长度为 2 的幂时，可用 `(n - 1) & hash` 快速定位；扩容后位置只有原位置或原位置加旧容量两种可能。

### D3-4 `ConcurrentHashMap` 如何保证线程安全？（🟡 理解但不流畅）

**回答骨架**：
- JDK 1.7：`Segment` 数组 + `HashEntry` 数组 + 链表；每个 Segment 继承 `ReentrantLock`，一个 Segment 管理一部分桶，使用分段锁。
- JDK 1.8：`Node` 数组 + 链表/红黑树；空桶插入通常使用 CAS，发生哈希冲突时对桶头节点使用 `synchronized`，锁粒度更细。
- 相比 `Hashtable` 或 `synchronizedMap` 的整张表加锁，ConcurrentHashMap 可以让不同桶之间并发操作，吞吐量更高。

**本轮复述记录**：
- 已掌握：JDK 1.7 的 Segment 分段锁，以及 JDK 1.8 的 Node + 链表/红黑树和桶级加锁。
- 待加强：JDK 1.8 空桶插入的 CAS 机制，以及与整表加锁容器的性能区别。

### D4-1 Java 线程有哪些状态？（🟢 基本掌握）

**回答骨架**：
- `NEW`：创建线程对象但尚未调用 `start()`。
- `RUNNABLE`：调用 `start()` 后，包含就绪和正在运行的状态；Java 没有单独的 `RUNNING` 状态。
- `BLOCKED`：等待获取 `synchronized` 监视器锁。
- `WAITING`：无期限等待，如 `wait()`、无参 `join()`、`LockSupport.park()`。
- `TIMED_WAITING`：限时等待，如 `sleep()`、带超时的 `wait()`/`join()`。
- `TERMINATED`：`run()` 执行结束，线程生命周期结束。

**本轮复述记录**：
- 已掌握：六种线程状态及其基本进入条件；知道 `RUNNABLE` 包含就绪和运行，`BLOCKED` 是等待锁，`WAITING`/`TIMED_WAITING` 分别是无限期/限时等待。

### D4-2 `start()` 和 `run()` 有什么区别？（🟢 基本掌握）

**回答骨架**：
- `start()` 会请求启动新的线程，使线程进入 `RUNNABLE`，由新线程执行 `run()`。
- 直接调用 `run()` 只是普通方法调用，在当前线程中执行，不会创建新线程，也不会产生并发效果。
- 同一个 Thread 对象的 `start()` 只能调用一次；重复调用会抛出 `IllegalThreadStateException`。
- 线程进入 `TERMINATED` 后不能回到 `RUNNABLE`，也不能重新启动；如需再次执行应创建新的 Thread 对象。
- Thread 对象不是线程工厂，而是线程的“控制器”。一个控制器只能启动一次，想再开线程，就 new 一个新的控制器。

**本轮复述记录**：
- 已掌握：`start()` 启动新线程并执行 `run()`；直接调用 `run()` 在当前线程执行；同一线程不能多次调用 `start()`。

### D4-3 `sleep()` 和 `wait()` 的区别？（🟢 基本掌握）

**回答骨架**：
- `sleep()` 属于 `Thread`，`wait()` 属于 `Object`。
- `sleep()` 让线程休眠但不释放已经持有的锁；`wait()` 让线程进入等待并释放当前对象的监视器锁。
- `wait()` 通常必须在持有对象锁的 `synchronized` 代码块或方法中调用。
- `sleep()` 到时间后自动恢复；`wait()` 可由 `notify()`/`notifyAll()`、中断或超时唤醒。
- `sleep()` 常用于延迟，`wait()` 常用于线程间通信。

**本轮复述记录**：
- 已掌握：`sleep()` 让线程休眠且不释放锁；`wait()` 让线程等待并释放当前对象锁，通常用于线程间通信。

### D4-6 `synchronized` 和 `Lock` 的区别？（🟢 基本掌握）

**回答骨架**：

### D4-7 `volatile` 有什么作用？能保证线程安全吗？（🟢 基本掌握）

- 适合做状态标志；需要复合操作的原子性时使用锁或原子类。

**本轮复述记录**：
- 已掌握：`volatile` 保证可见性和有序性，但不保证原子性，因此不能单独保证线程安全。

### D4-8 什么是 CAS？有什么优缺点？（🟢 基本掌握）

**回答骨架**：
- CAS 是 Compare-And-Swap，包含内存位置 `V`、预期旧值 `A` 和新值 `B`。
- 如果 `V == A`，就原子地把 `V` 更新为 `B`；否则更新失败，线程可以自旋重试。
- 优点：非阻塞，避免线程阻塞/唤醒和上下文切换，低竞争下性能较好。
- 缺点：高竞争时自旋浪费 CPU；只能覆盖有限的原子更新场景；存在 ABA 问题。
- `AtomicInteger`、AQS 等并发工具底层会使用 CAS。
- 总结：CAS 通过比较当前值和预期值是否相同，决定是否更新为新值；它是无锁并发的重要基础，但存在自旋开销和 ABA 问题。
- 补充：自旋 -> 失败就一直试，费 CPU；ABA -> 值没变，但中间被人动过，CAS 发现不了；无锁并发 -> 不加锁，靠「比较再交换」保证安全，失败就重试

**本轮复述记录**：
- 已掌握：CAS 通过比较当前值和预期值是否相同，决定是否更新为新值；是无锁并发的重要基础，但存在自旋开销和 ABA 问题。

### D6-1 JVM 如何判断对象是否可以回收？什么是 GC Roots？（🟢 基本掌握）

- JVM 主要通过可达性分析判断对象是否存活。

- GC Roots 是垃圾回收时作为遍历起点的一组特殊对象。
- 常见 GC Roots：虚拟机栈中的局部变量、方法区中的静态变量和常量、正在运行的线程、本地方法引用等。
- 不可达不代表一定立即回收，只是具备回收条件。

**本轮复述记录**：
- 已掌握：可达性分析的基本过程，以及 GC Roots 作为起点寻找对象的作用；能说出虚拟机栈局部变量、方法区静态变量和常量等常见 GC Roots。

### D6-2 常见垃圾回收算法有哪些？（🟡 理解但不流畅）

**回答骨架**：
- 标记-清除：标记存活对象，清除未标记对象；简单但会产生内存碎片。
- 复制算法：将存活对象复制到另一块区域，清空原区域；没有碎片，但需要额外空间，适合存活率低的年轻代。
- 标记-整理：标记存活对象并向一端移动，再清理边界外空间；没有碎片但需要移动对象和更新引用。
- 分代回收：根据对象存活时间划分新生代和老年代，分别采用更适合的算法。
- 内存碎片：空闲空间分散在多个存活对象之间，总空闲空间可能足够，但没有足够大的连续空间分配对象。

**本轮复述记录**：
- 已掌握：四种算法的基本流程、优缺点和新生代/老年代的常见算法选择。
- 已理解：标记-清除只清理垃圾、不移动存活对象，会留下分散的空闲小块，形成内存碎片。

### D6-3 Minor GC、Major GC 和 Full GC 的区别？（🟢 基本掌握）

**回答骨架**：
- Minor GC / Young GC：主要回收新生代，频率较高、通常较快。
- Major GC / Old GC：主要回收老年代，通常比 Minor GC 慢；不同收集器对术语定义可能略有差异。
- Full GC：回收整个堆，通常还可能涉及方法区，停顿时间最长、影响最大。
- 新生代空间不足常触发 Minor GC；老年代空间不足、晋升失败、分配担保失败等可能触发 Full GC。

**本轮复述记录**：
- 已掌握：Minor GC 主要回收新生代，Major GC 主要回收老年代，Full GC 回收整个堆且停顿影响最大。

### D6-4 OOM 如何排查？（🟢 基本掌握）

**回答骨架**：
- 先根据错误信息判断溢出区域：Java heap、Metaspace、Direct Memory 或 native thread。
- 结合日志和监控观察堆、老年代、元空间、线程数等指标。
- 堆溢出时通过 `-XX:+HeapDumpOnOutOfMemoryError` 生成堆转储，使用 MAT/VisualVM 分析大对象和引用链。（堆转储相当于使给 JVM 的堆内存怕一张“案发现场照片”）

- 区分代码泄漏、JVM 配置不足、线程/直接内存不足，再针对性修复；不能只通过增大堆内存掩盖问题。

**本轮复述记录**：
- 已掌握：先定位内存区域，再结合监控和堆转储分析大对象及 GC Roots，判断内存泄漏、配置不足或线程/直接内存问题并修复。

### D8-1 为什么 InnoDB 使用 B+ 树作为索引结构？（🟢 基本掌握）

**回答骨架**：
- B+ 树的非叶子节点主要存 key 和子指针，叶子节点存放数据记录或对应主键，因此单个节点能容纳更多 key，树高较低，磁盘 I/O 次数较少。
- B+ 树的叶子节点通过链表连接，定位起点后可以顺序扫描，范围查询效率高。
- 普通二叉树分支少，数据量大时树高较高，磁盘 I/O 多。
- B 树的非叶子节点也存数据，单个节点能存放的 key 和指针相对更少；叶子节点通常没有 B+ 树那样的链表连接，范围查询不如方便。
- 哈希索引精确匹配很快，但不适合范围查询、排序和前缀匹配。

**本轮复述记录**：
- 已掌握：B+ 树非叶子节点存 key/指针、树高较低、I/O 少、叶子链表支持范围查询，以及与二叉树、B 树、哈希表的对比。
- 表述优化：普通二叉树节点通常是一个 key 加最多两个子指针；树高不能绝对说固定为两三层。

### D8-2 聚簇索引和非聚簇索引有什么区别？（🟢 基本掌握）

**回答骨架**：
- 聚簇索引的叶子节点存放完整行数据；InnoDB 通常使用主键作为聚簇索引，一个表只能有一个。
- 没有主键时，InnoDB 会选择合适的唯一非空索引；如果没有，会使用隐藏行 ID。
- 非聚簇索引也称二级索引，叶子节点存索引列值和对应主键值，不存完整行数据。
- 通过二级索引找到主键后，再到聚簇索引查询完整数据，称为回表。
- 查询所需字段都能从二级索引获取时，称为覆盖索引，可以避免回表、减少 I/O。

```二级索引
叶子节点：
索引列 + 主键
        ↓
如果 SQL 还需要其他字段
        ↓
拿主键去聚簇索引找
        ↓
回表


如果 SQL 需要的字段
索引里已经全部存在
        ↓
不用去聚簇索引
        ↓
覆盖索引
```

**本轮复述记录**：
- 已掌握：聚簇索引/二级索引的叶子节点内容、一个表只能有一个聚簇索引、回表和覆盖索引。
- 表述优化：`SELECT *` 通常不容易被二级索引覆盖，但不是绝对必然回表。

### D9-1 联合索引的最左前缀法则？（🟡 理解但不流畅）

**回答骨架**：
- 联合索引 `(a, b, c)` 的查找通常要从最左列 `a` 开始，不能跳过中间列。
- `WHERE a = 1` 和 `WHERE a = 1 AND b = 2` 可以使用索引。
- `WHERE b = 2` 缺少最左列，通常不能有效使用该联合索引。
- `WHERE a = 1 AND c = 3` 可以使用 `a` 定位，但跳过 `b` 后，`c` 通常不能继续用于联合索引定位，只能作为额外过滤条件。
- 最左前缀描述的是联合索引的有序查找过程，不只是“每列分别排序”。

**本轮复述记录**：
- 已掌握：`a`、`a+b` 可以利用 `(a,b,c)` 联合索引，单独 `b` 不行。
- 待加强：跳过中间列时，前面的列仍可能使用，但后续列不能完整参与索引定位。

### D9-2 联合索引遇到范围查询后有什么影响？（🟢 基本掌握）

**回答骨架**：
- 对联合索引 `(a,b,c)`，`a = 1 AND b > 2 AND c = 3` 中，`a` 和 `b` 可以用于索引定位。
- `b` 已经是范围查询后，`c` 通常不能继续用于索引范围定位；MySQL 可能通过索引条件下推对 `c` 做额外过滤。

**本轮复述记录**：
- 已掌握：范围查询不会让前面的索引失效，但后面的联合索引列通常不能继续用于定位。

### D9-3 哪些情况可能导致索引失效或无法充分利用？（🟡 理解但不流畅）

**回答骨架**：
- 联合索引跳过最左列；
- 对索引列使用函数、计算或表达式；
- 发生隐式类型转换；
- `LIKE '%abc'` 以通配符开头；`LIKE 'abc%'` 通常可以利用索引；
- 不合理使用 `OR`；
- 范围查询后面的联合索引列通常不能继续用于索引定位。

**本轮复述记录**：
- 已掌握：最左列缺失、范围查询、前导 `%` 模糊查询会影响索引使用。
- 待加强：函数计算、隐式类型转换和 `OR` 对索引的影响；范围查询不是让整棵索引失效，而是影响后续列的定位。

### D10-1 事务的 ACID 四大特性？（🟢 基本掌握）

**回答骨架**：
- **原子性（Atomicity）**：事务中的操作要么全部成功，要么全部失败回滚。
- **一致性（Consistency）**：事务执行前后都要满足数据库约束和业务规则，数据从一个合法状态转移到另一个合法状态。
- **隔离性（Isolation）**：并发事务之间相互隔离，具体隔离程度由隔离级别决定。
- **持久性（Durability）**：事务提交后数据持久保存，即使宕机也能通过日志等机制恢复。

**本轮复述记录**：
- 已掌握：原子性、一致性、隔离性、持久性的基本含义。
- 表述优化：一致性要强调约束和业务规则；持久性针对已提交数据，之后仍可被新事务修改。

### D10-2 MySQL 事务隔离级别及并发问题？（🟢 基本掌握）

**回答骨架**：
- 读未提交：可能脏读、不可重复读、幻读。
- 读已提交：避免脏读，但可能不可重复读和幻读。
- 可重复读：避免脏读和不可重复读，InnoDB 默认隔离级别；幻读要区分快照读和当前读。
- 串行化：通过串行执行事务避免三类问题，但并发性能最低。
- 脏读：读到其他事务尚未提交的数据；不可重复读：同一事务两次读同一行结果不同；幻读：同一条件两次查询的结果集行数或记录集合发生变化。

- 已掌握：四种隔离级别与脏读、不可重复读、幻读的对应关系；能解释三类并发问题。
- 待加强：InnoDB 可重复读下快照读、当前读与幻读防止机制的区别。
